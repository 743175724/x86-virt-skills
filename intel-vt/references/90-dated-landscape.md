### Mandatory instruction to the reading agent

Any answer that depends on a fact from this file **must tell the user that it is a dated snapshot taken on 2026-09-16, and must be re-verified against the vendor's own official source before being acted on.** Do not present anything below as the current state of the world. If the user's question turns on whether something is available, shipping, merged, priced or supported *today*, say that this skill cannot know and name the page to check (Microsoft Learn page, Intel support article, cloud provider release notes, kernel changelog, vendor pricing page).

### Fastest-decaying category — read this before quoting anything below

Windows build numbers and default-on policy, product support matrices, cloud GA/preview status, pricing, market share, kernel merge status and roadmaps are **the fastest-decaying and the most frequently mis-reported** class of fact in this whole domain. They decay in months, and secondary sources routinely promote a preview to "GA", collapse an announcement into a ship date, attach a default-on policy to the wrong Windows release, or repeat a vendor's own benchmark as an independent result. The Azure TDX case in `errata.md` (E15) is the canonical example: a public preview announced 2023-11-15 was widely recorded as a December 2023 GA, and the actual first Azure TDX GA came more than two years later.

## 90.1 Windows: versions, defaults and requirements

This is the section a Windows PC question lands in. Every other chapter that names a Windows feature deferred its version numbers, its edition gating and its default-on policy here, because those are exactly the facts that change between two Windows releases while the mechanism underneath does not.

### 90.1.1 Which Windows a PC is on

- **Claim.** `[GA]` Windows 10 reached end of support on **2025-10-14**; version 22H2 was its final version, and after that date Windows 10 receives no quality, feature or security updates outside the paid Extended Security Updates programme. Any PC still on Windows 10 is therefore outside the servicing stream that delivers the security defaults described below.  `[no-spec]` `[646]` `C:high` `V:dated`
- **Claim.** `[GA]` Windows 11 25H2 (RTM build **26200**, released 2025-10) continues to enable virtualization-based security and memory integrity by default. The build number and the release month reach this skill only through a secondary relay of Microsoft's release information, not from a Learn page this rebuild read; see `15-security.md` §15.7 for the mechanism and verify the build before quoting it.  `[no-spec]` `[552]` `C:low` `V:dated`

### 90.1.2 VBS, memory integrity and Credential Guard: which builds, which hardware

- **Claim.** `[GA]` Microsoft Learn states that **starting in Windows 11 22H2 and Windows Server 2025, Credential Guard is enabled by default** on domain-joined, non-domain-controller systems that meet the hardware requirements, and that this default enablement automatically turns virtualization-based security on; see `15-security.md`, which owns the feature.  `[no-spec]` `[633]` `C:high` `V:dated`
- **Claim.** `[GA]` That default enablement is applied **without UEFI lock**, so an administrator can still disable it remotely, and it does **not** overwrite an existing setting: a device on which Credential Guard was explicitly disabled before the upgrade stays disabled afterwards. This is the single most common reason a machine on a qualifying build does not show the feature running; see `15-security.md`.  `[no-spec]` `[633]` `C:high` `V:dated`
- **Claim.** `[GA]` On Windows 11 Pro and Pro Education 22H2 and later, VBS and Credential Guard may be enabled automatically if the device meets the other requirements **and has previously run Credential Guard** — the Pro SKUs are not unconditionally in scope the way the domain-joined Enterprise case is; see `15-security.md`.  `[no-spec]` `[633]` `C:medium` `V:dated`
- **Claim.** `[GA]` **Memory integrity (HVCI) is on by default on clean installs of Windows 11 on compatible hardware.** Before Windows 11 the default-on case was much narrower — clean installs of Windows 10 in S mode only — so "memory integrity is on by default" is a Windows 11 fact, not a Windows fact; mechanism in `15-security.md` §15.7.  `[no-spec]` `[634]` `C:high` `V:dated`
- **Claim.** `[GA]` The hardware qualification is a platform checklist rather than a CPU flag: hardware virtualization enabled in UEFI/BIOS (Intel VT-x), Secure Boot capability, an IOMMU, and the UEFI tables that describe them. A machine that fails any one of these will not have VBS or memory integrity turned on by default however new its processor is; see `15-security.md` and `12-vtd-faults-bios-siov.md`.  `[no-spec]` `[476][634]` `C:high` `V:dated`
- **Claim.** `[announced]` Microsoft's rollout sequence, as relayed by secondary sources rather than read from Learn in this rebuild, is that 24H2 added a **UEFI lock** that makes VBS harder to disable, and that memory integrity is to be pushed on by default to more **existing** devices through quality updates, rather than only to clean installs, from **2026-10**. That date falls after this file's as-of date, so the second half is an announcement and not an observed rollout; the earlier wording asserted it in the past tense, which no source dated 2026-09 or before could support. Verify both against Microsoft's own pages before quoting; mechanism in `15-security.md` §15.7.  `[no-spec]` `[552][627]` `C:low` `V:dated`
- **Claim.** `[GA]` The practical consequence of all of the above, reported consistently across community sources, is that the Windows hypervisor is resident from early boot on a default-configured Windows 11 PC even when the Hyper-V feature is not selected, so third-party type-2 hypervisors and Android emulators must have VBS disabled to take full control of VT-x. Quoted performance costs vary by more than a factor of four across sources and are treated as unresolved in `errata.md` O4.  → mechanism in `15-security.md` §15.7 and `17-windows-platform.md` §17.1.  `[no-spec]` `[552]` `C:low` `V:dated`

### 90.1.3 The driver blocklist and drivers incompatible with memory integrity

- **Claim.** `[GA]` Since the **Windows 11 2022 Update**, the Microsoft vulnerable-driver blocklist is enabled by default on all devices and can be toggled from the Windows Security app; it is additionally enforced whenever memory integrity, Smart App Control or S mode is active. The list is refreshed quarterly and also through the monthly servicing updates, so its contents are dated by construction and are not reproduced in this skill.  `[no-spec]` `[635]` `C:high` `V:dated`
- **Claim.** `[GA]` Separately from the blocklist, a kernel driver must satisfy the HVCI code-integrity rules to load at all while memory integrity is on, and Microsoft ships both a driver-compatibility test in the hardware lab kit and an incompatible-driver report in the Windows Security app. Which specific products are currently incompatible changes continuously; treat any list of them as stale on sight and see `15-security.md` for why the enforcement exists.  `[no-spec]` `[483][649]` `C:medium` `V:dated`

### 90.1.4 The Windows Hypervisor Platform and the third-party VMMs that moved onto it

- **Claim.** `[GA]` The Windows Hypervisor Platform is a separate optional Windows feature from the Hyper-V role, enabled independently (`Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform`), which is why a machine can present the platform API to a third-party VMM without the Hyper-V management stack being installed.  `[no-spec]` `[465][644]` `C:medium` `V:dated`
- **Claim.** `[GA]` The API dates from the **Windows 10 April 2018 Update (version 1803)** era: Microsoft posted the WHPX accelerator patch series to the QEMU list in January 2018, and Microsoft's own Xamarin-era documentation states that "on Windows 10 October 2018 Update (RS5) and higher, Windows Hypervisor Platform (WHPX) is available for automatic use when Hyper-V is enabled". No current Learn page was found that states the introducing build directly, so the date rests on those two.  `[no-spec]` `[644][645]` `C:medium` `V:dated`
- **Claim.** `[GA]` Hyper-V itself is edition-gated: it is an optional feature on Windows 10 and Windows 11 **Pro, Enterprise and Education only** and cannot be installed on Home, and it requires a 64-bit processor with second-level address translation and VM monitor mode extensions. A Home-edition PC therefore reaches the platform through WSL2, Windows Sandbox is unavailable to it, and its virtualization-based security still runs.  `[no-spec]` `[636]` `C:high` `V:dated`
- **Claim.** `[GA]` VMware's own documentation states that the Windows Hypervisor Platform is **not supported on Windows Server editions**, which is why VMware Workstation's host VBS mode is unavailable there; no Microsoft page stating the restriction in those terms was located, so this is a vendor relay about a Microsoft feature. See `17-windows-platform.md` §17.3.  `[no-spec]` `[642]` `C:medium` `V:dated`
- **Claim.** `[GA]` For **VMware Workstation Pro 17**, Broadcom documents "host VBS mode": it is entered automatically when Workstation is launched on a capable Windows 10 or later host with Hyper-V enabled, VMs in that mode may run more slowly because of the platform-API feature set, and Intel VT-x is **not** available to their guests — so a Workstation VM in host VBS mode cannot itself run Hyper-V or virtualization-based security. See `14-nested-virtualization.md`.  `[no-spec]` `[642]` `C:high` `V:dated`
- **Claim.** `[GA]` The widely repeated origin of that support — **Workstation/Player 15.5.5 or later on Windows 10 20H1 or later**, with the "automatically install Windows Hypervisor Platform" box ticked at install time — reaches this skill only through Chinese secondary sources; VMware's own 15.5.5 release note was not located, so the version pair should be checked against Broadcom's release notes before being quoted.  `[no-spec]` `[648]` `C:low` `V:dated`
- **Claim.** `[GA]` **VirtualBox 6.0** introduced the Native Execution Manager, which runs the VM on the Windows hypervisor when a Hyper-V component is active instead of failing with `VERR_VMX_NO_VMX`; Oracle's administrator's guide documents the coexistence and states that performance in that mode is lower than with direct VT-x. See `17-windows-platform.md` §17.3.  `[no-spec]` `[643]` `C:medium` `V:dated`
- **Claim.** `[GA]` **QEMU** carries the platform API as its `whpx` accelerator, contributed by Microsoft in January 2018 and documented as usable on x86_64 and arm64 Windows hosts alongside its other backends.  `[no-spec]` `[644]` `C:high` `V:dated`
- **Claim.** `[GA]` **Intel HAXM is retired.** Intel's repository states that HAXM v7.8.0 is the last release and gives the reason directly: "Today both Microsoft Hyper-V and macOS HVF have added support for Intel Virtual Machine Extensions. We have therefore decided to retire the HAXM project." The standalone third-party accelerator driver on Windows was made redundant by the platform API, not by a change in the hardware.  `[no-spec]` `[647]` `C:high` `V:dated`
- **Claim.** `[GA]` On the Android side the succession is: HAXM deprecated from **emulator 33.x.x.x** and replaced on Intel processors by the Android Emulator Hypervisor Driver (AEHD), with the emulator ceasing to use HAXM entirely from **36.2.x.x**.  `[no-spec]` `[482][647]` `C:medium` `V:dated`
- **Claim.** `[announced]` Google has announced that **AEHD will sunset on 2026-12-31**, and Android Studio already offers Windows users a conversion from AEHD to the Windows Hypervisor Platform — so the end state on Windows is that the emulator runs on Hyper-V like every other third-party VMM.  `[no-spec]` `[482]` `C:medium` `V:dated`

### 90.1.5 Utility VMs: WSL2, Windows Sandbox, Docker Desktop, Application Guard

- **Claim.** `[GA]` **WSL 2** requires Windows 10 version 1903 **build 18362.1049** or later on x64, or Windows 10 version 2004 **build 19041** or later on ARM64; builds below 18362 cannot run WSL 2 at all, and the **Virtual Machine Platform** optional component must be enabled. Enabling that component is what makes the machine a hypervisor host; see `17-windows-platform.md` §17.4.1.  `[no-spec]` `[640]` `C:high` `V:dated`
- **Claim.** `[GA]` **Windows Sandbox** requires Windows 11, or Windows 10 version 1903 / **build 18305** or later, in the Pro, Enterprise or Education editions — it is not offered on Home SKUs — on AMD64 with virtualization enabled in firmware, 4 GB of RAM minimum and 8 GB recommended.  `[no-spec]` `[639]` `C:high` `V:dated`
- **Claim.** `[GA]` **Docker Desktop** on Windows requires Windows 10 64-bit **22H2 (build 19045)** or Windows 11 64-bit **23H2 (build 22631)** or higher in the Enterprise, Pro or Education editions, a 64-bit processor with second-level address translation, hardware virtualization enabled in firmware and 8 GB of RAM; its default WSL 2 backend requires **WSL 2.1.5** or later, and enhanced container isolation requires **WSL 2.6** or later because it depends on a Linux kernel of at least 6.3.  `[no-spec]` `[641][481]` `C:high` `V:dated`
- **Claim.** `[GA]` Docker Desktop's Hyper-V backend is available only with an all-users installation, and a third backend, Docker VMM, is documented as beta — so "Docker on Windows" is not one virtualization path but a choice between three, each resting on the hypervisor.  `[no-spec]` `[641]` `C:medium` `V:dated`
- **Claim.** `[GA]` **Microsoft Defender Application Guard is gone.** It is deprecated and, **starting with Windows 11 version 24H2, is no longer available**, including the Windows Isolated App Launcher APIs; Application Guard for Office is likewise deprecated together with the `Windows.Security.Isolation` APIs, and Microsoft's own recommendation for container-based isolation is Windows Sandbox or Azure Virtual Desktop. `17-windows-platform.md` §17.4.4 keeps the mechanism as a worked example; it is no longer a feature a current PC can enable.  `[no-spec]` `[478]` `C:high` `V:dated`

### 90.1.6 Hyper-V nested virtualization: versions and version-dependent restrictions

- **Claim.** `[GA]` The prerequisites are a Hyper-V host on **Windows Server 2016 or later, or Windows 10 or later**, a **VM configuration version of 8.0 or higher**, and on Intel a processor with VT-x and EPT. The configuration version matters as much as the Windows version: a VM imported from an older host keeps its old configuration version and will refuse nesting until it is upgraded. See `14-nested-virtualization.md` for the mechanism.  `[no-spec]` `[637]` `C:high` `V:dated`
- **Claim.** `[GA]` Nesting is enabled per virtual machine, from the physical host, **while the VM is off**: `Set-VMProcessor -VMName <VMName> -ExposeVirtualizationExtensions $true`.  `[no-spec]` `[637][479]` `C:high` `V:dated`
- **Claim.** `[GA]` The documented restriction that bites first is memory: with Hyper-V running inside a VM the VM must be turned off to change its memory, so **runtime memory resize does not work and dynamic memory does not fluctuate** even when it is switched on. Enabling nesting does not make either of them work.  `[no-spec]` `[637]` `C:high` `V:dated`
- **Claim.** `[GA]` Microsoft states that **virtualization applications other than Hyper-V are not supported inside a Hyper-V virtual machine and are likely to fail** — so "nested virtualization is enabled" does not imply that an arbitrary third-party VMM will run in the guest, only that Hyper-V-based workloads will. See `14-nested-virtualization.md`.  `[no-spec]` `[637]` `C:medium` `V:dated`
- **Claim.** `[GA]` Whether checkpoints, live migration and save/restore are permitted for a VM with virtualization extensions exposed has changed across Windows Server releases and was **not captured verbatim from the current Learn page in this rebuild**; treat any statement about those three as unverified and read the page before answering a question that turns on them.  `[no-spec]` `[637]` `C:low` `V:dated`
- **Claim.** `[GA]` The same switch is what allows a Windows guest to run the utility VMs of §90.1.5 and to enable virtualization-based security inside a VM — without the host exposing virtualization extensions, a nested Windows Sandbox, WSL2 instance or VBS-enabled guest cannot start. See `14-nested-virtualization.md` and `17-windows-platform.md` §17.7.  `[no-spec]` `[637][479]` `C:medium` `V:dated`

### 90.1.7 Hyper-V scheduler defaults by edition and version

- **Claim.** `[GA]` On **Windows Server 2016** the classic scheduler is the default and the core scheduler is optional; from **Windows Server 2019** onward the **core scheduler is the default**. This is the version-level complement to the mechanism in `17-windows-platform.md` §17.2.8.  `[no-spec]` `[638][485]` `C:high` `V:dated`
- **Claim.** `[GA]` On **client** Windows, from **Windows 10 version 1803** onward the **root scheduler** is the default, and Microsoft states it is the *only supported* hypervisor scheduler configuration on client systems: administrators should not attempt to override it. A Windows PC therefore has no scheduler choice to tune, which disposes of most "which Hyper-V scheduler should I use" questions before they start.  `[no-spec]` `[638][485]` `C:high` `V:dated`
- **Claim.** `[GA]` The root scheduler arrived with that same release, Windows 10 version 1803, handing work scheduling to the root partition's own NT scheduler — so on a client PC the scheduling of every virtual processor, including those of WSL2 and Sandbox, is done by the Windows kernel scheduler rather than by the hypervisor.  `[no-spec]` `[638]` `C:high` `V:dated`

### 90.1.8 Client silicon under a Windows PC

- **Claim.** `[GA]` **Panther Lake (Core Ultra 300)** launched at CES on **2026-01-05** as Intel's first Intel 18A client SoC. Intel disclosed no new client VMX or TDX features with it; TDX remains Xeon-only and client parts still carry only VT-x and VT-d.  `[no-spec]` `[591]` `C:medium` `V:dated`

The architectural facility itself is owned by `06-address-translation.md` and the feature by `15-security.md`; what is dated here is Microsoft's generation-level guidance.  `[no-spec]` `[634]` `C:medium` `V:dated`
