## 2. Correction owed to an **existing** entry — `[201]`, outside the 540–549 range

This pass downloaded and text-extracted the actual Intel PDF, which resolves the metadata `[201]`
itself flags as unverified. `[201]` currently reads:

```
[201] Intel. Intel 5520 Chipset and Intel 5500 Chipset Specification Update (errata #47 and #53,
      interrupt-remapping unit reliability). Specification update issued 2011-09.
      https://edc.intel.com — T1 (document metadata not verified against the Intel PDF; cited at C:low)
```

Verified replacement (cover page and revision history read directly from the PDF):

```
[201] Intel. Intel 5520 and Intel 5500 Chipset Specification Update. Document Number 321329-015US, February 2015. Erratum #47 "Intel VT-d: Receiving two identical interrupt requests in back to back cycles may corrupt attributes of remapped interrupt, or hang subsequent interrupt-remap-cache invalidation command"; erratum #53 "Intel VT-d: In-flight remap-able interrupts not drained on interrupt invalidation command". https://www.intel.com/content/dam/www/public/us/en/documents/specification-updates/5520-and-5500-chipset-ioh-specification-update.pdf — T1
```

Evidence:

- Cover: `Intel® 5520 and Intel® 5500 Chipset / Specification Update / Febuary 2015` *(Intel's own
  typo)* `/ Document Number: 321329-015US`.
- The "2011-09" in the present entry was revision **-014**, not the current document: the revision
  history records "September 2011 — -014 — Added C-2 Stepping to Summary Table of Changes".
- The document's scope is the 5520/5500 IOH only. `grep -c X58` over the full extraction returns
  **0**, which is why chapter 12 no longer attributes X58 to this document.
- Both errata carry the same workaround text, quoted in §12.8.3: BIOS sets bit 25 at Dev/Func 14/4
  offset 168h and de-features interrupt remapping by clearing ECAP_REG.IR (bit 3) and the
  INTR_REMAP bit in the ACPI DMAR Flags field.
- Affected device IDs 3403h/3406h; steppings B-3 → revision 13h and C-2 → revision 22h.

Because the metadata is now verified against the Intel PDF, the `C:low` grade the old entry imposed
on the two §12.8.3 claims has been lifted: the 5500/5520 claim is now `C:high` and the
mitigation/X58 claim `C:medium`.

## 4. Source-access notes for anyone reproducing this pass

- All seven Intel PDFs were downloaded fresh and text-extracted. The installed `pdftotext` is
  **xpdf 4.06**, which has a **`-table`** mode — `pdftotext -table -f <p> -l <p> file.pdf -`. This is
  the only reliable way to read the multi-column tables in these documents: both default and
  `-layout` extraction shift the number column against the name column by one row in VT-d Table 30,
  VT-d Chapter 11 register tables, ABI Table 5.4 (SEAMCALL leaf numbers) and ABI Table 5.247
  (TDCALL leaf numbers). Plain `pdftotext` additionally **drops the first line of every bulleted
  sub-condition** in VT-d Table 30 (LCT.4.x, LGN.1.x, RTA.1.x, SCT.4.x, SPT.4.x, SGN.4.x, SGN.8.x);
  PyMuPDF recovers those.
- A **stale TDX Connect PDF** is a trap here. One content endpoint still serves
  `354629 001-US March 2023`. The revision `[17]` records, `354629 003-US June 2025`, is served from
  `https://cdrdv2.intel.com/v1/dl/getContent/773614` and was confirmed from that cover page.
- `git.kernel.org` blocks `WebFetch` (HTTP 403) but serves `curl` fine; `lore.kernel.org` is behind
  an Anubis challenge and cannot be fetched either way. Use
  `curl https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/patch/?id=<sha>`.
