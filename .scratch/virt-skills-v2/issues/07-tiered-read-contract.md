# 07 分层读取与 token 预算契约

Type: grilling
Status: resolved
Blocked by: 06

## Question

**技能宣传的体积比真实体积小约 5 倍，这是 token 预算小的 agent 直接死掉的原因。**

`intel-vt/SKILL.md:31` 写 "Chapters `01`–`18` run 310–570 lines each"，
`amd-virtualization/SKILL.md:32` 写 "300–500 lines each"，
`docs/DEPLOYMENT.md:141` 再重复一遍。按行数没错。但平均行长 **184 字符**（Intel）/ 152（AMD）：

| 文件 | 行 | 字节 | 约 token | 最长行 |
|---|---|---|---|---|
| `intel-vt/references/13-tdx.md` | 568 | 104,500 | **~26.1k** | 909 |
| `intel-vt/references/04-vm-entry.md` | 415 | 68,688 | ~17.2k | 966 |
| `amd-virtualization/references/14-sev-snp.md` | 477 | 79,749 | ~19.9k | 737 |

两个 corpus 合计：Intel `references/` 约 **290k token**，AMD 约 **258k token**。

于是 `intel-vt/SKILL.md:49` 那句 "**Stop.** One chapter plus `errata.md` answers almost everything"
——对一个 TDX 问题来说是 **32k token**。照 `SKILL.md:50-51` 再拉第二章，一个答案 **45k token**。
预算小的 agent 如果无视指令直接 glob 目录，当场死亡。

还有一处误导：`SKILL.md:31-32` 说 `90-dated-landscape.md` 和索引文件"更短"——
它 180 行但 39,515 字节（约 10k token），**按真正要紧的度量比四个架构章节都大**。

**要决定的：**

1. **分层契约长什么样。** 一个 agent 在预算受限时，如何只读它需要的那一段？
   候选：章节内分节可寻址（`index.json` 已经带 section `headings`）；
   每章加一个 200 token 的摘要头；把 claim 的元数据（`[1]` `C:high` `V:durable`）
   挪出正文行；拆分超大章节（`13-tdx.md`、`14-sev-snp.md`）。
2. **体积怎么标注。** 行数是错的度量。改成字节？估算 token？
   `index.json` 已经有 `bytes` 和 `sha256` 字段，`SKILL.md` 要不要直接引用它们。
3. **claim 行格式要不要动。** 现在每条事实是一行
   `- **Claim.** <200-900 字符散文>  [SDM 3C §27.9.1] [1] C:high V:durable`。
   Intel 侧 2650 条 × 约 4 个元数据 token ≈ **10k token 的尾注**。
   **但这个格式正是这套资产可信的原因，不能为省 token 牺牲它。**
   问题是：查"bit 7 是什么"要读一段 900 字符的散文，而按 grep 做部分读取会从中间截断 claim。

## 依赖

必须先有 06 的结论：技能是一个还是两个，决定了分层是在技能内做还是跨技能做。

## Answer

### 核心结论：问题不是章节太大，是**读取粒度错了**

实测（2026-09-26，由 `index.json` 的 `bytes` 与 `headings` 算得）：

| 层 | intel-vt | amd-virtualization |
|---|---|---|
| 全部章节 | **295k tok** | **266k tok** |
| `index.json` 整体 | 10.9k tok | 9.0k tok |
| **单章 index 条目** | 中位 **322 tok**（最大 581） | 中位 **268 tok**（最大 429） |
| **单个小节** | 平均 **1,071 tok** | 平均 **1,241 tok** |
| 整章 | 最大 **26,393 tok** | 最大 **20,157 tok** |
| 小节总数 | 275 | 214 |

**一个小节比整章小约 20 倍。** 现行指令"读一章 + errata"对 TDX 问题要花 32k；
同一个问题在小节粒度上是 **约 1.4k**（一条 index 条目 + 一个小节）。

### 1. 分层读取契约

**四层，每层都有实测成本，agent 按预算停在能停的那层。**

| 层 | 读什么 | 成本 | 什么时候停在这层 |
|---|---|---|---|
| **T0** | `SKILL.md` | 目标 < 5k tok | 总是加载。它只做路由，不含事实 |
| **T1** | `index.json` 里**该章的那一条** | **~300 tok** | 确认选对了章，并拿到它的 `headings` 列表 |
| **T2** | **一个小节** | **~1.1k tok** | **绝大多数问题到此为止** |
| **T3** | 整章 | 15–26k tok | 只有当问题横跨全章时 |

一次典型回答 = T0 + T1 + T2 ≈ **`SKILL.md` 之外约 1.4k tok**。

**三档预算下的行为**，直接写进 `SKILL.md`：

- **8k 预算**：T0 → T1 → T2，**禁止 T3**。装不下就回答"这个问题需要整章，当前预算不够"，
  而不是读一半然后猜。
- **32k 预算**：T0 → T1 → T2，必要时**一次** T3。绝不读第二章。
- **128k 及以上**：同上，允许 T3 加 `errata.md`。**即便如此也不要 glob 目录**——
  561k tok 的语料没有任何预算装得下。

### 2. 缺失的机制：小节寻址

章节文件**不是**按小节可寻址的，这是 T2 无法实现的唯一原因。
但**不需要拆分文件**——`index.json` 每章已带精确的 `headings` 文本，
所以小节抽取是一个可执行操作，写进 `SKILL.md` 即可：

> 从 `index.json` 取该章的 `headings`，选中目标小节的标题文本，
> 抽取**从该标题起到下一个同级标题止**的区间。

**不拆分 `13-tdx.md`（26k）。** 它的小节平均只有 ~1k tok；
拆文件会增加路由复杂度而换不到任何东西。

### 3. 体积怎么标注：不再手写数字

现行 `SKILL.md:31` 的 "310–570 lines" 按行数没错，但**按真正要紧的度量低估约 5 倍**
（平均行长 184 / 152 字符）。而且它是**手写的，必然漂移**。

**改为：`SKILL.md` 不再写任何体积数字，改为指向 `index.json` 的 `bytes` 字段。**
那是生成的，永不漂移。同时更正那条误导——`90-dated-landscape.md` 不是"更短"，
它 39,515 字节（约 10k tok），**比四个架构章节都大**。

### 4. claim 元数据格式：**不动**

全语料 4,729 条 claim × 约 4 个元数据 token ≈ **19k tok 的尾注**——听起来该优化。

**但那是整章读取下的数字。在小节粒度上，一节约 4 条 claim × 4 tok ≈ 16 tok，可以忽略。**

> 也就是说：元数据开销**从来不是格式问题，是粒度问题**。
> 而这个格式**正是整套语料可信的原因**（`README.md` 开头那段就是为它写的）。
> **粒度修好之后，没有任何理由去动它。**

原 ticket 担心的"查'bit 7 是什么'要读一段 900 字符散文"同样由 T2 解决：
读的是那一个小节，不是整章。

### 5. 合并后的 `SKILL.md` 装得下吗——装得下

06 把厂商路由、quickref 导航三节、约 46 章的路由表都压给了 `SKILL.md`，
而规范建议 body < 5000 tok。估算：

| 内容 | 估算 |
|---|---|
| 厂商路由 + 分层读取协议 | ~800 tok |
| 症状 → 章节（两侧合并去重） | ~1,000 tok |
| 46 章路由表（每行约 15 tok） | ~700 tok |
| 表 → 归属章节 | ~500 tok |
| 五个 Windows 一行答 | ~200 tok |
| 输出标准 + 范围边界 | ~700 tok |
| **合计** | **~3.9k tok** ✅ |

**关键的结构取舍**：`SKILL.md` 只路由到**章名**，不描述章节内容；
描述在 `index.json`（T1）里按需读。
这条取舍是整个契约成立的原因——**没有它，46 章的描述会把 body 撑爆。**

### 交给 11 的结论

无文件系统宿主的"蒸馏版"**不是一份独立维护的文档，而是 T0 层本身**。
如果 T0 做对了（< 5k tok、只路由不含事实），它**就是**蒸馏版。
11 要解决的只剩：references 怎么送达那三家宿主。
