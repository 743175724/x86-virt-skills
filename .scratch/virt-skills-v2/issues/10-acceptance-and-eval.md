# 10 v2 的验收标准与 eval 扩展

Type: grilling
Status: open
Blocked by: 06, 07, 08, 09

## Question

**这张图的终点是一份 spec。这个 ticket 决定那份 spec 交出去之后，怎么判断 v2 做成了。**

现有的验收机制是真实存在且有分量的——不要推翻它，要扩展它：

- `eval/` 每个技能 80 题的 golden set，外加 `eval/RUNNER.md` 共享评分协议。
- 回答与评分**必须由不同的 agent 做**，且在全新 session 里跑。
- 现有成绩：Intel 427/447（95.5%）事实召回、80/80 路由正确、0 误述；
  AMD 两轮 497/508 与 495/512、引用有效性 100%。
- 评分者有权把答案键标记为 `key-disputed` 并去查规范——
  两轮里**发现答案键错的次数多于技能错的次数**（Intel 5 条、AMD 4 条）。

**要决定的：**

1. **"各大 AI 用得明白"怎么变成可测的。** 这是用户的首要诉求，但现有 eval
   全部在单一宿主里跑，测的是**内容召回**，测不出**路由与加载**。
   需要一类新测试：同一批问题，在 Claude Code / Codex / Kimi / 其他宿主上分别跑，
   看技能**有没有被触发**、**有没有加载对章节**。
   这比内容题更难自动化——要在本 ticket 里定出可执行的协议。
2. **开发题怎么出、怎么评。** 08 如果选了"给可编译骨架"，
   那验收就不是答对事实而是**代码能不能跑**。
   评分者要不要真的编译并加载？在哪台机器上？用户的 265KF 是唯一的真机。
3. **按型号查询题怎么出。** 09 的型号表建成后，要能回答
   "我这颗 265KF 上 X 成不成立"。这类题的答案键从哪来——
   如果 AMD 客户端确实没有公开勘误通道，那部分题的正确答案就是
   **"无法确定，且这是已知缺口"**，评分者必须认这种答案为满分，否则会训练出编造。
4. **回归门。** 现在 CI 跑 lint 和 build --check，不跑 eval（`README.md:171-173` 明说）。
   v2 改了结构之后，怎么确保 2531 条 claim 没在搬运中损坏？
   `index.json` 已有每章 `sha256`——能不能变成一道回归门？
5. **什么叫"做完"。** 给出一组具体的、能判定真假的完成条件。
   不接受"更好用"这种表述。
