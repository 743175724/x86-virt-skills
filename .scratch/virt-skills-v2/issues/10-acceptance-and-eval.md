# 10 v2 的验收标准与 eval 扩展

Type: grilling
Status: resolved
Blocked by: 06, 07, 08, 09

## Question

**这张图的终点是一份 spec。这个 ticket 决定那份 spec 交出去之后，怎么判断 v2 做成了。**

现有的验收机制是真实存在且有分量的——不要推翻它，要扩展它：

- `eval/` 每个技能 80 题的 golden set，外加 `eval/RUNNER.md` 共享评分协议。
- 回答与评分**必须由不同的 agent 做**，且在全新 session 里跑。
- 现有成绩：Intel 427/447（95.5%）事实召回、80/80 路由正确、0 误述；
  AMD 两轮 497/508 与 495/512、引用有效性 100%。
- 评分者有权把答案键标记为 `key-disputed` 并去查规范——
  两轮里**发现答案键错的次数多于技能错的次数**（Intel 5 条、AMD 4 条）。

**要决定的：**

1. **"各大 AI 用得明白"怎么变成可测的。** 这是用户的首要诉求，但现有 eval
   全部在单一宿主里跑，测的是**内容召回**，测不出**路由与加载**。
   需要一类新测试：同一批问题，在 Claude Code / Codex / Kimi / 其他宿主上分别跑，
   看技能**有没有被触发**、**有没有加载对章节**。
   这比内容题更难自动化——要在本 ticket 里定出可执行的协议。
2. **开发题怎么出、怎么评。** 08 如果选了"给可编译骨架"，
   那验收就不是答对事实而是**代码能不能跑**。
   评分者要不要真的编译并加载？在哪台机器上？用户的 265KF 是唯一的真机。
3. **按型号查询题怎么出。** 09 的型号表建成后，要能回答
   "我这颗 265KF 上 X 成不成立"。这类题的答案键从哪来——
   如果 AMD 客户端确实没有公开勘误通道，那部分题的正确答案就是
   **"无法确定，且这是已知缺口"**，评分者必须认这种答案为满分，否则会训练出编造。
4. **回归门。** 现在 CI 跑 lint 和 build --check，不跑 eval（`README.md:171-173` 明说）。
   v2 改了结构之后，怎么确保 2531 条 claim 没在搬运中损坏？
   `index.json` 已有每章 `sha256`——能不能变成一道回归门？
5. **什么叫"做完"。** 给出一组具体的、能判定真假的完成条件。
   不接受"更好用"这种表述。

## Answer

### 1. "各大 AI 用得明白"怎么变成可测的

**06 的合并把这题削掉了一半。** 合并之前有两类失败——"选错技能"和"选对技能但读错章"；
合并之后**"选错技能"这一类不存在了**（只有一个技能）。剩下两问，都可观测：

| 探针 | 问什么 | 判定 |
|---|---|---|
| **触发** | 技能有没有被激活 | agent 是否读了 `SKILL.md` |
| **路由** | 读的是不是该读的那一章 | agent 实际打开的 `references/` 路径 == 预期路径 |

**路由探针的格式**：`{问题, 预期章节路径, 预期小节}`。
按 07 的分层契约，**正确行为是 T0 → T1 → T2**，所以评分同时看
"读对了吗"和"**读多了吗**"——读整章而非小节记为**部分失败**，因为那正是要修的毛病。

**必须在每个目标宿主上各跑一遍**（Claude Code / Codex / Kimi），
这是现有 eval 测不到的维度——它全部在单一宿主里跑，测的是内容召回。
**这类测试无法进 CI**（需要多宿主、需要观察工具调用），
与现有 eval 同样属于"人工在全新 session 里跑"的那一类。

### 2. 开发题：按**陷阱清单**评分，不按相似度

08 定下的判据落地为：

> 给出部件名（例："写出每处理器的 VMXON 上下文分配与 teardown"），
> 要求 agent 写出该部件，**按已知陷阱清单逐条检查**。
> **不踩已记录的陷阱才算过。**

这比"答对事实"客观得多，因为陷阱是**枚举的**。开张的四条已经有了（见 08）。
评分者不需要判断代码"好不好"——只需要判断它有没有踩进清单里的坑。

**不要求编译。** CI 里没有硬件，而"编不过"和"编得过但会崩"对本轨道是同一类失败。
陷阱清单覆盖后者，而后者才是真正伤人的那个。

### 3. 按型号查询题：**"查不到"必须给满分**

这条是防捏造的关键，且已有先例——现有评分协议已授权评分者标记 `key-disputed`
并去查规范。这里需要一条对称的授权：

> 当正确答案是 **"无法确定，且这是一个已记录的缺口"** 时，
> 给出该答案并**正确指出缺口范围**的回答**记满分**。
> 把"我不知道"判为失分，会把语料训练向编造——
> **而这正是本仓库存在的理由所要防的那件事。**

12 之后缺口窄而明确（不再是"AMD 客户端什么都没有"，而是三条带日期的具体缺口），
所以"正确指出缺口范围"是可判定的，不是主观的。

### 4. 回归门：`sha256` 已经在那儿了，**只差用起来**

`index.json` 每章已带 `sha256`。v2 的搬运会改路径，**但不应改内容**。因此：

> **搬运前后，每一章的 `sha256` 必须一致——除非该章在本次提交中被有意编辑，
> 且编辑在 commit message 中列明。**

这是个可机械执行的门，能挡住"搬运中损坏 4,729 条 claim"这类最可怕的失败。
按本仓库规矩，**加门之前先注入一次违例证明它会响**。

现有两道闸门（`lint.mjs` / `build.mjs --check`）在搬运中继续生效且必须保持 clean，
其中 12 新增的**规则 4c** 与 05 新增的**孤儿资源规则**一并纳入。

### 5. 什么叫"做完"——可判真假的清单

不接受"更好用"。v2 完成当且仅当以下全部成立：

**结构**
1. 只有一个技能，`SKILL.md` 的 body **< 5000 tok**（实测，非估算）
2. `references/intel/`、`references/amd/`、`references/dev/` 三棵子树就位，
   `[N]` 作用域在各自子树内，lint 拒绝跨树引用
3. AMD 章节里 **11 处指向 intel-vt 的路径全部解析成功**（现在是 404）
4. `00-quickref` 的导航三节已上移进 `SKILL.md`

**读取**
5. `SKILL.md` 里没有任何**手写**的体积数字，全部指向 `index.json` 的 `bytes`
6. 分层读取协议（T0→T1→T2）写进 `SKILL.md`，含小节抽取的具体操作
7. 路由探针：**触发率 100%**；**路由正确率不低于现有的 80/80**
8. 抽样 20 题，**中位额外读取量 < 3k tok**（对照现行"一章 + errata"的 32k）

**内容**
9. 开发轨道覆盖 08 列出的全部部件，每个部件标注 Intel/AMD 分叉点
10. 故障轨道开张 5 条全部就位，**每条都写出真实成因**（不是观察到的型号范围）
11. 事实召回率**不低于**现有的 95.5% / 97.8%
12. 误述（misconception）**保持 0**

**机械**
13. `lint.mjs` 与 `build.mjs --check` clean
14. `sha256` 回归门就位并已由注入证明非空转
15. 三个目标宿主上各装一次，技能均可见（Kimi 侧走 `.agents/` 或 `.kimi-code/`）

### 6. eval 自身要改什么

- **两套 golden set 合并为一套**，每题保留 `vendor:` 标签，因为按 06 现在只有一个技能。
  原有 160 题不重写——它们测的是内容，内容没变。
- **新增三类题**：路由探针、开发部件题、按型号查询题（含"应答缺口"的题）。
- `eval/RUNNER.md` 增补两条授权：**读多了算部分失败**、**正确应答缺口记满分**。
- 现有的"回答与评分必须由不同 agent 完成、在全新 session 里跑"**不变**。

### 7. 一条必须保留的已知局限

现有 README 已诚实记录：评分者与回答者来自**同一模型家族**，
跨模型复核只做过一次（47 题里分歧 1 题，且裁决下来**原评分者是对的**）。
**那是方差测量，不是偏差测量。** v2 不改变这一点，也不应假装改变了——
真正的测试需要来自不同厂商的评分者。这条继续写在 Known limits 里。
