# 11 无文件系统宿主的技能包形态与体积约束

Type: grilling
Status: resolved
Blocked by: 06, 07

## Question

由 01 从迷雾中毕业。01 推翻了原先的假设——**无文件系统的宿主要的不是粘贴式长 prompt，
而是符合规范的技能包**。三家都落在这一类：

- **Kimi 网页 / APP**：Skills 面板托管
- **ChatGPT 网页 / 移动端**：独立技能进不去，**必须打成 plugin**
- **claude.ai / Cowork**：frontmatter 只接受规范的六个字段（本仓库恰好全合规）

所以目标形态仍是 `SKILL.md` + `references/`。**真正的约束是体积**：

> Agent Skills 规范建议 body **< 5000 token**。
> 本仓库两个 corpus 合计约 **548k token**，单章最大 `13-tdx.md` 约 **26k token**。

差了两个数量级。

**要决定的：**

1. **蒸馏到什么粒度。** 5000 token 的 body 装不下任何一章，只装得下路由。
   那么蒸馏版是"路由 + 精选事实"，还是"路由 + 按需从网络拉取 references"？
   后者要求宿主能联网取文件——**这一点必须先验证，不能假设**。
2. **丢什么。** 这是最难的一问，也是最容易毁掉这套资产的一问。
   现有内容的价值来自 claim 级的规范锚点（`[SDM 3C §30.2.1]` `[1]` `C:high` `V:durable`）。
   **蒸馏时如果把锚点丢了，剩下的就是一份"读起来很权威但没人能核对"的东西——
   正是 README 开头声明要避免的那种东西。** 所以：宁可少讲，不可去锚。
   这条要在本 ticket 里定成硬规则。
3. **ChatGPT 的 plugin 形态。** 01 查明独立技能进不去、必须打成 plugin。
   plugin 的清单格式、体积上限、以及它能不能承载 `references/` 目录，都要查清。
   **这可能需要一个独立的 research ticket**，视 06 的结论而定。
4. **蒸馏版与完整版的一致性怎么保证。** 两份内容一旦分叉，就会漂移。
   `index.json` 已有每章 `sha256`——能不能让蒸馏版由完整版**生成**而非手写，
   并进 `tools/build.mjs --check` 的漂移门？

## 依赖

- **06**：技能是一个还是两个，决定蒸馏版是一个包还是两个。
- **07**：分层读取契约。蒸馏版本质上就是分层的最上面一层——
  如果 07 把分层做对了，蒸馏版可能是它的自然副产品，而不是一份独立维护的东西。

## 待查缺口（01 遗留）

**Kimi 网页能否直接上传现成的 `SKILL.md` 技能包？**
帮助页只写了三条路径：面板一键添加、社区下载、上传文档生成，
没说能不能直传规范包。这决定本 ticket 该产出什么格式。
开工前需要先确认，必要时拆成一个小的 research ticket。

---

## Answer

### 07 已经把本 ticket 的主体解决了：**蒸馏版不是一份独立文档，它就是 T0 层**

07 定下的分层契约里，`SKILL.md`（T0）被要求**只路由、不含事实、目标 < 5k tok**，
估算落在 **~3.9k tok**。

> **规范建议 body < 5000 token。T0 的设计目标本来就是这个数。**
> 所以"蒸馏"这件事不存在——**做对 T0 就等于做出了蒸馏版。**

这推翻了本 ticket 开篇的框架。原问题问"蒸馏到什么粒度、丢什么"，
预设了要从 561k tok 压缩到 5k，那确实是两个数量级、必然失真。
**实际不需要压缩任何东西**：T0 从来就不承载事实，它承载路由。

### 1. 因此第 2 问（丢什么）自动消解——**一条 claim 都不丢**

原 ticket 最担心的是"蒸馏时把规范锚点丢了，剩下一份读起来很权威但没人能核对的东西"。

**T0 里本来就没有 claim，所以没有锚点可丢。**
这条担心在正确的结构下不成立，**硬规则也就不必立**——
真正的硬规则已经在 07 里：**T0 不含事实**。

### 2. 真正剩下的问题：references 怎么送达那三家宿主

三家（Kimi 网页、ChatGPT 网页/移动端、claude.ai/Cowork）**都接受符合规范的技能包**
（01 查明），不是粘贴式 prompt。所以形态是 `SKILL.md` + `references/`，
问题只是**体积与上传通道**。

| 方案 | 说明 | 判断 |
|---|---|---|
| **A. 整包上传** | T0 + 全部 references（561k tok 的文件，但**不是一次加载**——宿主按需取） | **首选**，前提是通道允许多文件 |
| **B. T0 + 按需联网取 references** | 技能包只含 T0，章节从公开 URL 取 | **需先验证宿主能联网取文件，不得假设**。且仓库当前是 **private**，要取就得先公开 |
| **C. 只上传 T0** | 退化为"知道去哪查但查不到" | **不可接受**——它会让模型凭记忆补全，正是本仓库存在的理由所要防的 |

**结论：走 A，B 作为通道不支持多文件时的退路，C 明确排除。**

### 3. 第 4 问（一致性）：蒸馏版必须是**生成的**，不是手写的

既然 T0 就是蒸馏版，一致性问题自动消失——**只有一份 `SKILL.md`**。
但打包这件事应当进 `tools/build.mjs`，并纳入 `--check` 的漂移门，
理由与现有生成物（`index.json`、`AGENTS.md`、`agents/openai.yaml`）完全一致：
**手写的副本必然漂移，生成的不会。**

### 4. 未决缺口（不猜，留着）

- **Kimi 网页能否直传规范技能包**——01 未能确认，帮助页只写了
  面板一键添加 / 社区下载 / 上传文档生成三条。**这决定 A 还是 B。**
- **ChatGPT 的 plugin 形态**：01 查明独立技能进不去、必须打成 plugin。
  其清单格式、体积上限、能否承载 `references/` 目录**均未查**。
- **仓库是 private**，B 方案需要先决定是否公开。这是产品决定，不是技术决定。

这三条都是**通道事实**，不是设计问题。任何一条都不该靠推断作答——
按仓库惯例，查不到就声明缺口。
