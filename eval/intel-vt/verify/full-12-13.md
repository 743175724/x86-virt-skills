### Extraction method — and why it matters here

The installed `pdftotext` is **xpdf 4.06**, which has a **`-table`** mode. It is the only reliable
way to read these documents' multi-column tables: both default and `-layout` extraction shift the
number column against the name column by one row in VT-d Table 30, the VT-d Chapter 11 register
tables, ABI Table 5.4 and ABI Table 5.247. Plain `pdftotext` additionally **drops the first line of
every bulleted sub-condition** in VT-d Table 30 (LCT.4.x, LGN.1.x, RTA.1.x, SCT.4.x, SPT.4.x,
SGN.4.x, SGN.8.x); PyMuPDF recovers those. TDX-BASE Figures 7.1 and 7.2 are vector state diagrams
whose text layer is unordered — those were read by rendering the page and by coordinate extraction.

Two traps found and avoided:

- A content endpoint still serves **TDX Connect 354629 001-US, March 2023**. The revision the
  bibliography records, 354629 003-US June 2025, comes from `…/getContent/773614`.
- **ABI §5.4.81 (TDH.VP.ENTER) misprints its own leaf number as 10** — `TDH.VP.CREATE`'s value. It
  reproduces under all three extraction modes, so it is a defect in 348551-008US, not a column
  shift. Table 5.4 and TDX-BASE Table 2.3 both give 0. The chapter now carries a note so a future
  re-checker does not "correct" it the wrong way.

## 2. Findings — every WRONG, with the correction

### W1 — `12-vtd-faults-bios-siov.md:47` — fault compression stated as mandatory

Was: "Hardware compares the source-id of the currently faulting request against the SID field of
each Fault Recording Register whose F field is Set, and does not record the fault information if it
finds a match."

VT-d §7.2.1 makes it optional:

> "**If hardware supports compression**¹ of multiple faults from the same requester, it compares the
> source-id (SID) field of each Fault Recording Register with Fault (F) field Set, to the source-id
> of the currently faulted request. If the check yields a match, the fault information is not
> recorded."
> … "If the above check does not yield a match (**or if hardware does not support compression of
> faults**), hardware checks the Fault (F) field of the Fault Recording Register referenced by the
> internal index."

Footnote 1: "Hardware implementations supporting only a limited number of fault recording registers
are **recommended** to collapse multiple pending faults from the same requester." §11.4.7.6 agrees:
"hardware **may** collapse additional faults from the same source-id (SID)."

Now states that compression is optional, that implementations without it skip the check, and that
the specification only recommends it for units with few fault recording registers.

### W2 — `12-vtd-faults-bios-siov.md:401` — the same error, load-bearing in the security section

§12.8.1 concluded that "a device generating a storm of identical faults will not fill the fault
log". On an implementation without compression it **will**, and will drive PFO. Now conditioned on
compression support, with the without-compression case stated.

### W3 — `12-vtd-faults-bios-siov.md:367` — a self-reference that had gone stale

Was: "secondary sources and **the skill's own bibliography entry** describe it as Rev 1.0".

`references/bibliography.md` entry `[21]` already reads "Order 337679-002, **Rev 1.1**… (cover reads
Rev 1.1; the widely-cited 'Rev 1.0' is wrong)", and `[204]` likewise. The claim contradicted the
repository it ships in. Now: secondary sources still cite Rev 1.0; the bibliography already records
Rev 1.1. The cover reading itself is re-confirmed —
`September 2020 / Order Number: 337679-002, Rev 1.1` — and the revision history shows **1.0 was the
June 2018 technical-preview release**, which the chapter now says. Anchor moved to `[no-spec]`: the
cover and revision history are front matter with no section number, and CONVENTIONS forbids
inventing one.

### W4 — `12-vtd-faults-bios-siov.md:382` — SIOV's third translation stage misdescribed

Was: "…and the PASID-table entry selects first-level, second-level, pass-through or nested
translation" as **stage 3**.

SIOV §3.1 puts the type selection in stage 2 and makes stage 3 the walk:

> "2. … the PASID structure entry can be programmed to specify first-level, second-level,
> pass-through or nested translation, along with references to first-level and second-level
> page-table structures.
> 3. Finally, the address in the request is subject to address translation using the first-level,
> second-level or both page-table structures, depending on the type of translation function."

"Three-stage address translation" is the spec's own term and stages 1 and 2 were right; only the
third item was misplaced. Now stated correctly, with an explicit note that the type is chosen at
stage 2.

### W5 — `12-vtd-faults-bios-siov.md:417` — X58 attributed to a document that does not mention it

Was: "in the Intel **5500/5520/X58** chipset specification update as errata #47 and #53", anchored
`[VT-d 5.20 Ch.?]`.

The document is **"Intel 5520 and Intel 5500 Chipset Specification Update", Document Number
321329-015US, February 2015**. `grep -c X58` over its full extraction returns **0**. Its errata read:

> **47.** "Intel VT-d: Receiving two identical interrupt requests in back to back cycles may corrupt
> attributes of remapped interrupt, or hang subsequent interrupt-remap-cache invalidation command."
> **53.** "Intel VT-d: In-flight remap-able interrupts not drained on interrupt invalidation command."

The X58 counterpart is **erratum #69** in the separate X58 Express Chipset Specification Update,
identified by Linux commit `803075dba31c` ("x86/iommu/vt-d: Expand interrupt remapping quirk to
cover x58 chipset", Neil Horman, 2013-07-17): "It turns out this same problem is present in the
intel X58 chipset as well. See errata 69 here". Intel's X58 spec-update URL now redirects into a
404, so that half stays kernel-attested.

The anchor was also fabricated: VT-d Rev 5.20 contains **zero** occurrences of "5500", "5520",
"X58" or "erratum" outside the copyright-page boilerplate. It documents no chipset errata at all.
Now `[no-spec]` with `[201]`, per the brief's instruction, and the claim carries the verbatim
erratum titles and the document number.

### W6 — `12-vtd-faults-bios-siov.md:418` — same fabricated anchor on the mitigation claim

Content was correct but unsourced. Re-anchored `[no-spec]`, and the claim now carries the errata's
own workaround text: "BIOS to set bit 25 in (Dev/Func: 14/4, Offset: 168h). De-feature interrupt
remapping capability by clearing Interrupt-Remap (IR) RWO field (bit 3) in Extended Capability
Register and clearing INTR_REMAP bit (bit 0) in Flags field of ACPI DMAR tables", plus the affected
device IDs 3403h/3406h.

Because `[201]`'s metadata is now verified against the Intel PDF, the `C:low` grade both claims
carried has been lifted to `C:high` / `C:medium`.

### W7 — `13-tdx.md:142` — SEAMCALL RAX bit 24 is not reserved

Was: "bits **62:24** are reserved and must be 0 unless a specific leaf defines them."

ABI Table 5.2, §5.4.1, printed page 93:

> `24  INTERRUPT_MODE  Pending interrupts detection mode: 0: Pending interrupts are detected only
> if the host VMM's RFLAGS.IF is 1. 1: Pending interrupts are detected regardless of the host VMM's
> RFLAGS.IF status. Support of INTERRUPT_MODE is enumerated by
> TDX_FEATURES0.HOST_SIDE_INTERRUPT_MODE (bit 62)… INTERRUPT_MODE is ignored by non-interruptible
> interface functions.`
> `62:25  Reserved  Must be 0`

The "unless a specific leaf defines them" hedge does not save it: INTERRUPT_MODE is defined in the
**common** table. Now states bit 24 = INTERRUPT_MODE, bits 62:25 reserved, and bit 63 = P-SEAMLDR
dispatch (which the chapter previously rendered only as "must be 0").

### W8 — `13-tdx.md:252` — the import-side OP_STATE chain does not start at RUNNABLE

Was: "migration states such as START_EXPORT, LIVE_EXPORT, PAUSED_EXPORT, START_IMPORT,
MEMORY_IMPORT, STATE_IMPORT and LIVE_IMPORT are entered **from RUNNABLE** by the migration leaves."

TDX-BASE Figure 7.2 (printed p.75) shows only START_EXPORT entered from RUNNABLE. The import chain
begins at **UNINITIALIZED** and only rejoins RUNNABLE at the end:

> `UNINITIALIZED` —`TDH.IMPORT.STATE.IMMUTABLE`→ `START_IMPORT` / `MEMORY_IMPORT`
> `MEMORY_IMPORT` —`TDH.IMPORT.STATE.TD`→ `STATE_IMPORT` —`TDH.IMPORT.TRACK`→ `POST_IMPORT`
> —`TDH.IMPORT.COMMIT`→ `LIVE_IMPORT` —`TDH.IMPORT.END`→ `RUNNABLE`

Confirmed independently from the figure's text layer, which contains the adjacency
`UNINITIALIZED … TDH.IMPORT.STATE.IMMUTABLE … START_IMPORT`. Now states both chains explicitly.
The first clause (the `TDH.MEM.*` / `TDH.MR.EXTEND` self-loops) was correct and is kept.

### W9 — `13-tdx.md:416` — TEE_TCB_INFO does not measure the "active" module

Was: "it carries the TEE_TCB_SVN and the SHA-384 hashes of the **active** SEAM module's code image
**and of its provider's signature**."

Both halves are wrong. ABI Table 3.47:

> `MRSEAM  24  48  The measurement of the TDX Module **that created the TD** on the current platform.`
> `MRSIGNERSEAM  72  48  **Set to all 0's.**`
> `ATTRIBUTES  120  8  **Set to all 0's.**`
> `TEE_TCB_SVN2  128  16  TEE_TCB_SVN of the **current** TDX Module on the current platform.`

TDX-ISA Table 6-5 explains the zeros: "If the SEAM module was provided by Intel, this field is zero
and is marked invalid." The provider-signature hash therefore never carries a value under TDX. Now
gives the field offsets, distinguishes the TD-creating module (MRSEAM, TEE_TCB_SVN) from the
current one (TEE_TCB_SVN2), and records that MRSIGNERSEAM and TEE_TCB_INFO.ATTRIBUTES are zeroed.

### W10 — `13-tdx.md:420` — migrated-TD measurement timing inverted, and a wrong anchor

Was: "the TDX Module measurement in the report is that of the ***current*** module on the
destination platform **at the time the report is generated**."

ABI Table 3.47 says the opposite for MRSEAM:

> "**TD Migration:** For a TD which has been migrated, this is the measurement of the TDX Module on
> the destination platform, **at the time of destination TD creation (TDH.MNG.CREATE), before
> import**."

Only TEE_TCB_SVN2 is "at the time TDREPORT_STRUCT is generated by TDG.MR.REPORT". TDX-BASE §12.7.1
corroborates. The anchor was also wrong: ABI §3.9.2 is TDREPORT_STRUCT and contains no migration
text; the migration notes are in §3.9.3. Now distinguishes the two SVNs and explains why they can
differ after a TD-preserving module update. Re-anchored `[TDX-ABI §3.9.3]` `[TDX-BASE §12.7.1]`.

### W11 — `13-tdx.md:490` — TDX Connect host leaves do not start at 96

Was: "the corresponding host-side commands are the `TDH.TDI.*` and `TDH.MMIO.*` SEAMCALL leaves at
leaf numbers **96 and above**", anchored `[TDX-ABI §5.5.1]`.

Leaf 96 is `TDH.MIG.STREAM.CREATE` and 97 is `TDH.SERVTD.REBIND`; the TDX Connect block begins at
**128** with `TDH.IOMMU.SETUP` — which is the correction the earlier spot-check already applied to
§13.5, so the chapter contradicted itself. `TDH.TDI.*` occupy 136–141 and 164–166, `TDH.MMIO.*`
154–160. The anchor was also the **TDCALL** section; SEAMCALL is §5.4.1. Both fixed, and the
matching "above 96" wording in the §13.22 omissions list was corrected too.

## 3. Findings — UNSUPPORTED anchors (section resolves, does not carry the claim)
