## 3. Every WRONG, with the correction

Ordered by how badly a developer copying the text would be hurt.

### W1 — `08:204` — INVVPID types 1 and 3 are swapped

> "INVVPID type 1 … invalidates all mappings tagged with the descriptor's VPID, **except global translations**."

Ch.33: *"Single-context invalidation: If the INVVPID type is 1, the logical processor invalidates **all** mappings tagged with the VPID specified in the INVVPID descriptor."* Global translations are spared by **type 3**: *"Single-context invalidation, retaining global translations: If the INVVPID type is 3 … **except global translations**."* §31.4.3.1 agrees for both. As written the two types were indistinguishable and type 1 was understated, so a VMM using type 1 for a full per-VPID flush would believe it had left global entries live, and one using it expecting globals retained would over-flush.

### W2 — `08:259` — the allowed-0 polarity is inverted

> "bits 31:0 are the allowed-0 settings — a control whose bit is **0** there must be **0**"

App.A.3.1: *"VM entry allows control X … to be 0 **if bit X in the MSR is cleared to 0**; **if bit X in the MSR is set to 1, VM entry fails if control X is 0**."* A cleared allowed-0 bit is a *permission* to be 0, not an obligation. Read literally the claim forces every flexible control to 0, and it contradicts the OR-then-AND algorithm three claims later in the same section — that algorithm only works under the correct reading. Correct: allowed-0 bit = 1 ⇒ the control must be 1; allowed-1 bit = 0 ⇒ the control must be 0.

### W3 — `07:348` — VM entry does not perform posted-interrupt processing

> "VM entry also performs posted-interrupt processing when ON is set, so interrupts posted while the vCPU was not running are picked up at the next entry rather than lost."

No such behaviour exists in rev 092. §32.6: posted-interrupt processing *"is performed in response to the arrival of an interrupt with the posted-interrupt notification vector."* §29.3.2.5 gives VM entry's complete APICv action: *"VM entry loads the values of RVI and SVI from the guest interrupt-status field … the logical processor first causes PPR virtualization … and then evaluates pending virtual interrupts."* No PID, no ON. A VMM relying on this loses interrupts posted while the vCPU was descheduled until the next notification arrives; it must drain the PID into VIRR and RVI itself before entry.

### W4 — `07:362` and its pseudocode — posted-interrupt processing is mis-ordered

§32.6's seven steps are: **1** acknowledge the local APIC (yielding the physical vector) → **2** if the physical vector is not NV, take an ordinary external-interrupt VM exit → **3** clear ON atomically → **4** write zero to the local APIC's EOI register → **5** OR PIR into VIRR and clear PIR → **6** `RVI := max(old RVI, highest index set in PIR)`, **left unmodified if PIR was empty** → **7** evaluate. The chapter cleared ON *before* the acknowledge and dropped steps 2 and 4 entirely. §7.8.4's load-bearing argument — ON cleared before PIR is read — survives (step 3 precedes step 5) and is now stated that way.

### W5 — `08:140` — VMFUNC's #UD threshold, and disabled functions are not #UD

> "VMFUNC causes #UD … if **EAX is 63 or greater**, or if the bit of the VM-function controls selected by EAX is 0."

§28.5.7.2: #UD if *"the value of EAX is **greater than 63** (only VM functions 0-63 can be enable)"*; Ch.33's table reads "If EAX ≥ 64". **EAX = 63 is legal.** And a disabled function is explicitly not #UD: *"Otherwise, the instruction causes a **VM exit** if the bit at position EAX is 0 in the VM-function controls … the basic exit reason used is 59 (3BH)."*

### W6 — `07:82` and `07:84` — the APIC-access match is on the physical address

> "when EPT is in use the comparison is made against the **guest-physical** address of the access"

§32.4 footnote 1: *"Even when addresses are translated using EPT …, the determination of whether an APIC-access VM exit occurs depends on an access's **physical address, not its guest-physical address**."* The body agrees: the processor treats specially memory accesses "using linear addresses that translate to **physical addresses** in the 4-KByte APIC-access page". A guest-physical address matters only in that its EPT translation must land there.

### W7 — `08:217` — INVEPT and INVVPID do not have disjoint domains

> "Neither INVEPT nor INVVPID affects the other's mappings"

§31.4.3.1: *"Execution of the **INVVPID** instruction invalidates **linear mappings and combined mappings**"* and *"Execution of the **INVEPT** instruction invalidates **guest-physical mappings and combined mappings**."* Combined mappings are reachable by **both**. Only linear mappings are INVVPID-only, and only guest-physical mappings are INVEPT-only.

### W8 — `08:200`, `08:201`, `08:216` — EP4TA does not exist in rev 092

`EP4TA` occurs **0 times** in Vol.3C and 0 times in Vol.3D rev 092. The term is **EPTRTA** ("EPT root-table address"), 36 occurrences in Vol.3C, defined in §31.4.2 as bits 51:12 of the EPTP. The rename accompanied 5-level EPT, where the root is a PML5 table. The numeric substance was right; the name a reader would grep for was not. The earlier pass reported this for `06-address-translation.md`; chapter 08 still carried it.

### W9 — `07:207` — virtual-interrupt delivery has four conditions, not three

§32.2.2: *"(1) RFLAGS.IF = 1; (2) there is no blocking by STI; (3) there is no blocking by MOV SS **or by POP SS**; and (4) the **'interrupt-window exiting' VM-execution control is 0**."* The chapter listed three and read as exhaustive.

### W10 — `07:274` — the SDM says the opposite about re-evaluation

> "Evaluation of pending virtual interrupts is re-run after **every operation that can change RVI or VPPR**"

§32.2.1: *"Evaluation of pending virtual interrupts is caused only by VM entry, TPR virtualization, EOI virtualization, self-IPI virtualization, and posted-interrupt processing. **No other operations do so, even if they modify RVI or VPPR.**"* §32.1.3 closes PPR virtualization the same way. The practical consequence — a VMM's own write to VIRR or to the guest-interrupt-status field triggers nothing until the next VM entry — is the reverse of what the chapter implied.

### W11 — `07:78` and `07:161` — the virtual-APIC page may not be written under a running vCPU

§32.1: *"**With the exception of fields corresponding to virtualized APIC registers** (defined in Section 32.1.1), software may modify the virtual-APIC page referenced by the current VMCS of a logical processor in VMX non-root operation."* VIRR is one of those excepted fields, so "the VMM … may read and write it … it sets a bit in VIRR" is wrong for a running vCPU. RVI is also a VMCS field written with VMWRITE, not a virtual-APIC-page store.

### W12 — `08:110` — VMREAD's operands are the wrong way round in the prose

> "In 64-bit mode the **source** operand is 64 bits wide and can read an entire 64-bit field"

The source register carries the *field encoding*; Ch.33 scopes the width to the destination: *"The effective size of the **destination operand** … is always 32 bits outside IA-32e mode … and 64 bits in 64-bit mode."* The instruction-summary table at `08:46` had the order right; only this claim did not.

### W13 — `08:135` — VMCALL in virtual-8086 or compatibility mode

VMCALL's virtual-8086 and compatibility-mode exception tables both read *"#UD If executed **outside VMX non-root operation**"*, and its Operation tests for non-root operation before RFLAGS.VM and CS.L. A v8086 or compatibility-mode guest executing VMCALL takes a **VM exit**, not #UD.

### W14 — `08:255` — IA32_VMX_BASIC bit 56

App.A.1: *"If bit 56 is read as 1, software can use VM entry to deliver a hardware exception **with or without an error code, regardless of vector**."* It lifts the vector restriction on the *deliver-error-code bit*, not a restriction on the error-code *value* — §29.2.1.3 still requires bits 31:16 of the error code to be 0 either way.

### W15 — `08:277` — IA32_VMX_MISC bit 30

App.A.6: *"VM entry allows injection of a **software interrupt, software exception, or privileged software exception** with an instruction length of 0."* Not "an event": hardware exceptions, NMIs and external interrupts do not use the VM-entry instruction-length field at all.

### W16 — `08:28`, `08:29`, `08:30`, `08:31`, `08:32` — five over-general rules in §8.2

- **28** — the #UD-outside-VMX-operation list omitted **VMCALL** (and VMFUNC, whose condition is non-root operation). The rule is: every VMX instruction except VMXON.
- **29** — §33.1's compatibility-mode #UD sentence sits *before* the guest-available instructions and so covers the eleven VMM instructions only.
- **30** — VMFUNC has no CPL condition (§28.5.7.2 leaves it to the individual function); VMCALL's is "CPL ≠ 0 **and** in VMX root operation".
- **31** — **#AC occurs zero times in Ch.33** and cannot apply: alignment checking reports violations only at CPL 3, while every VMX instruction with a memory operand requires CPL 0.
- **32** — §28.1.2's unconditional-exit list **excludes VMREAD and VMWRITE** (they are §28.1.3, conditional) and includes VMCALL, SEAMCALL and TDCALL.

### W17 — `08:14` — VMFUNC has no VMX flag convention

Ch.33: *"Flags Affected — Depends on the VM function specified in EAX."* Twelve of the thirteen instructions use VMsucceed / VMfailInvalid / VMfailValid; VMFUNC does not. §33.2 also defines a fourth pseudo-function, `VMfail`.

### W18 — `08:139` — VMFUNC is not the only guest-available instruction

§33.1: *"The behavior of the **guest-available instructions** is summarized below: VMCALL … VMFUNC …"*. The claim contradicted this file's own claim at `08:55`. ECX is also not a general VMFUNC operand — Ch.33 encodes VMFUNC as ZO, and ECX is specific to VM function 0.

### W19 — `08:75` — the VMXON region need not be zeroed

§27.11.5: software should write the revision identifier to bits 30:0 of the first 4 bytes with bit 31 cleared, and *"**It need not initialize the VMXON region in any other way.**"*

### W20 — `08:80` — VMXOFF re-enables A20M only conditionally

Ch.33: VMXOFF *"unblocks INIT signals, **conditionally** re-enables A20M, and clears any address-range monitoring"*; the Operation does so only outside SMX operation. The address-range-monitoring effect was missing too.

### W21 — `07:83` — the APIC-access page's backing memory is not always irrelevant

§32.4.6.2: *"A physical access to the APIC-access page **may or may not** cause an APIC-access VM exit. If it does not cause an APIC-access VM exit, **it may access the APIC-access page** or the virtual-APIC page."* Which is precisely why the SDM recommends not setting the APIC-access address to any address used by physical accesses. The statement is true for linear and guest-physical accesses and false as an absolute.

### W22 — `07:43` — the post-entry TPR comparison needs "virtualize APIC accesses" too

§29.7.7: *"If the 'use TPR shadow' **and 'virtualize APIC accesses'** VM-execution controls are both 1 and the 'virtual-interrupt delivery' VM-execution control is 0, a VM exit occurs immediately after VM entry if …"*.

### W23 — `08:205` — the INVVPID descriptor is not ignored for type 2

The reserved-bit test `IF INVVPID_DESC[63:16] != 0 THEN VMfail(...)` precedes the type dispatch and therefore applies to type 2 as well. Only the VPID and linear-address *fields* are unused.

### W24 — `08:263` — wrong reason for IA32_VMX_PROCBASED_CTLS3's layout

App.A.3.4: *"This is because there are **64** tertiary processor-based VM-execution controls, while there were only **32** secondary processor-based VM-execution controls."* A size argument, not "no default-1 bits". The identical rationale is repeated in A.4.2 for IA32_VMX_EXIT_CTLS2.

### W25 — `08:291` — MAXPHYADDR is not always CPUID.80000008H:EAX[7:0]

App.A.1 footnote 2: *"If IA32_TME_ACTIVATE[0] = 1 …, MAXPHYADDR is **reduced by the value of IA32_TME_ACTIVATE[39:36]** when a logical processor is outside secure arbitration mode (SEAM …); the value is not reduced in SEAM."*

### W26 — `07:226` — virtual-interrupt delivery ceases recognition *before* delivering

§32.2.2's pseudocode order is: recompute RVI → SEAM clamp → **`cease recognition of any pending virtual interrupt`** → abort any transaction → enclave AEX → UINV check → deliver. The chapter delivered first and stopped recognising afterwards. It also omitted the UINV branch (§32.2.3), on which the EOI-exit bitmap is deliberately *not* consulted.
