## Answers (verbatim)

### trap-ept-qual-bit7 — 3/3

Bit 7 of the EPT-violation exit qualification is set if the **guest-linear-address
field of the VMCS is valid** for this VM exit. It says nothing about the
guest-physical-address field. It does **not** mean that *the guest-physical address
is valid*: the guest-physical-address field is filled on every EPT violation and
needs no validity flag — it always holds the address whose translation failed.
Bit 8 is defined only when bit 7 is set (clear = the access was to a guest
paging-structure entry during a page walk; set = it was the translation of a
guest-linear address). **Intel SDM Vol.3C §27.9.1** (field population per Vol.3C
§30.2.1); skill: `05-vm-exit.md` §5.4.6, `errata.md` E16.

### trap-ept-qual-bit6 — 4/4

No. The circulated reading that *bit 6 is the logical-AND of the XD bits* is wrong.
Bit 6 is the logical-AND of **bit 10 — user-mode execute access — of the EPT
paging-structure entries** used to translate the address, and it is defined only
when the "mode-based execute control for EPT" VM-execution control is 1; otherwise
it is undefined. It has nothing to do with the execute-disable bit of the guest's
own paging structures. Its companion is bit 5, the logical-AND of bit 2: plain
execute access when MBEC is off, supervisor-mode execute access when MBEC is on.
(The guest's own XD behaviour, where it is reported at all, appears at bit 11
under advanced VM-exit information, and only when bits 7 and 8 are both set.)
**Intel SDM Vol.3C §27.9.1**; skill: `05-vm-exit.md` §5.4.6, `errata.md` E17.

### trap-zombieload-cve — 4/4

ZombieLoad is **CVE-2018-12130**, the fill-buffer variant — MFBDS,
Microarchitectural Fill Buffer Data Sampling. The common answer, *"ZombieLoad is
CVE-2019-11091"*, is wrong: CVE-2019-11091 is **MDSUM** (Microarchitectural Data
Sampling Uncacheable Memory), a different member of the same family. MDS is four
distinct defects: CVE-2018-12126 MSBDS (store buffer), CVE-2018-12127 MLPDS (load
ports), CVE-2018-12130 MFBDS (fill buffers), CVE-2019-11091 MDSUM. All four are
covered by **INTEL-SA-00233**. Mitigation is microcode plus VERW with MD_CLEAR
(CPUID.07H.00H:EDX[10]), with MDS_NO (IA32_ARCH_CAPABILITIES bit 5) and FB_CLEAR
(bit 17) as the enumeration bits. **Intel SDM Vol.3C §28.1.2**; skill:
`15-security.md` §15.5.2, `errata.md` E18.

### trap-intel-asid — 4/4

Intel has **two** address-space identifier mechanisms, not none. **PCID** tags
linear-address translations by process context. **VPID** is a 16-bit VM-execution
control field in the VMCS that tags translations by virtual-processor / VM
context, invalidated with **INVVPID**. The claim that *Intel does not have an
ASID-like mechanism* is false. Nor is it true that *Intel flushes the TLB on every
VMX transition* — with "enable VPID" set, VM entry and VM exit do not invalidate
cached linear or combined mappings, so host and guest translations coexist in the
TLB and the VMM owns every invalidation correctness requires. VPID 0000H is
reserved for VMX root operation, and VM entry fails if "enable VPID" is 1 while
the VPID field is 0000H. Three mapping classes are tagged differently: linear
(VPID + PCID), guest-physical (EP4TA only), combined (all three) — which is why
INVVPID can never remove a guest-physical mapping. What is true is narrower:
Intel does not use the *name* ASID and does not use a single identifier for both
roles, whereas AMD's 32-bit ASID covers the VM-tagging role alone. **Intel SDM
Vol.3C §27.6.12** (and Vol.3A Ch.5 for PCID); skill: `06-address-translation.md`
§6.6, `errata.md` E19.

### trap-mbec-generation — 4/4

No. *MBEC was introduced with Skylake* is the misconception recorded as errata
E01. Mode-Based Execute Control first appeared in **Kaby Lake**, the
7th-generation Core parts of late 2016 to 2017. MBEC splits the EPT execute
permission into supervisor-mode execute (entry bit 2) and user-mode execute
(entry bit 10), so a single EPT entry can grant execute to supervisor-mode linear
addresses while denying it to user-mode ones; that is what makes it the hardware
accelerator behind **Windows HVCI**. The AMD counterpart, **GMET**, appeared in
Zen 2. Citation: `errata.md` **E01**, with the architectural definition at **Intel
SDM Vol.3C Ch.31** (`06-address-translation.md` §6.3.1).

### trap-pml-generation — 2/2

Page-modification logging was introduced with **Broadwell Xeon in 2015**, on the
server platform — first silicon was the Broadwell generation of Intel Xeon
processors. Attributions to a later microarchitecture are incorrect; *PML was
introduced with Skylake* is errata E02. **Intel SDM Vol.3C §27.6.18**; skill:
`06-address-translation.md` §6.8.

### trap-ept-walk-accesses — 4/4

Up to **24 memory accesses**, against at most 4 for a native 4-level walk. The
decomposition with 4-level guest paging and 4-level EPT is: 4 accesses to
translate the guest CR3 value through EPT, plus 5 for each of the 4 guest
paging-structure levels — 4 EPT accesses to translate that level's guest-physical
address, plus 1 read of the guest entry itself: 4 + 4 x (4 + 1) = 24. The widely
repeated *"up to 20 memory accesses"* counts only the EPT paging-structure reads
and omits the 4 reads of the guest paging-structure entries. 24 is the worst case
for a **cold** walk, not the expected cost of a TLB miss: paging-structure caches
cache upper levels of both hierarchies and mitigate it. **Intel SDM Vol.3C Ch.31**;
skill: `06-address-translation.md` §6.5, `errata.md` E03.

### trap-ooh-venue — 3/3

Out of Hypervisor was published at **SC'22 — the IEEE/ACM Supercomputing
conference, Dallas, November 2022**. **arXiv:2202.13483 (February 2022)** is the
preprint. The frequent attribution — that OoH *was published at SOSP*'22 — is
wrong. Be aware of a separate unresolved conflict: the paper's own reported
results differ between versions (13x / 6x / 16x in the SC'22 write-up versus about
14% checkpoint-time reduction and about 0.5% overhead in the arXiv abstract); say
which version a number comes from and do not merge them. Citation: `errata.md`
**E04** (and O6 for the results conflict); skill: `14-nested-virtualization.md`
§14.13.

### trap-sdm-vmx-chapter-numbers — 5/5

In SDM revision 092 (Vol.3C, order 326019-092, 2026-06) the VMX chapters are
**Vol.3C chapters 26 to 35**: 26 Introduction to VMX, 27 Virtual Machine Control
Structures, 28 VMX Non-Root Operation, 29 VM Entries, 30 VM Exits, 31 VMX Support
for Address Translation, 32 APIC Virtualization, 33 VMX Instruction Reference,
34 SMM, 35 SEAM. Alongside them, **Vol.3D App.A** carries the capability reporting
facility, **App.B** the VMCS field encodings and **App.C** the basic exit reasons.
There is **no chapter titled "Virtualization of System Resources"** — it no longer
exists, and neither do "Handling Boundary Conditions in a VMM" or "Managing
State". A citation to any of those titles, or to a VMX chapter number outside 26
to 35, comes from a stale manual — typically the 2017-era HTML mirrors. Cite
**Intel SDM Vol.3C Ch.26** onwards instead; skill: `00-quickref.md` §0.1,
`errata.md` E20.

### trap-vt-rp-specification — 5/5

I can't, because **there is no standalone Intel VT-rp specification** — no such
document exists. The normative content lives **only inside the SDM**: the
linear-address translation behaviour in **Vol.3A §5.5.1, §5.5.3 and §5.5.5**, the
VMCS fields in **Vol.3C §27.6.22**, and HLAT itself in **Vol.3C §31.2**. A citation
to a "VT-rp specification" is a fabricated source. For context, the three VT-rp
mechanisms are HLAT (the VMM owns translation of a chosen linear range, rooted at
HLATP with an HLAT prefix size field), paging-write access (restricts which pages
may act as paging structures) and guest-paging verification (checks that a
translation only went through such pages); together they are the hardware under
Microsoft's Hypervisor-enforced Paging Translation. **Intel SDM Vol.3C §31.2**;
skill: `06-address-translation.md` §6.10, `errata.md` E22.

### trap-tdxray-advisory — 4/4

There is no such pair: **TDXRay has no INTEL-SA advisory number, no CVE and no
CVSS score.** Intel's response was a security *announcement*,
**INTEL-2026-04-02-001, dated 2026-04-02**, which treats the behaviour as
architecturally permitted observation of shared microarchitectural resources and
places the mitigation burden on developers following Intel's side-channel-
resistance guidance. The widely repeated claim that *TDXRay is covered by
INTEL-SA-01271* is wrong: INTEL-SA-01271 is the **Intel Gaudi Software Installer
Advisory of 2025-05-13**, covering **CVE-2024-45067**, an incorrect-default-
permissions issue (CWE-276) in Gaudi software installers before version 1.18,
unrelated to TDX; the mislabel originates in link text on the TDXRay project site
whose href actually points at the announcement. TDXRay itself is peer-reviewed
research — IEEE Symposium on Security and Privacy 2026, authors from CISPA, UC San
Diego and Google. Contrast **CVE-2025-30513**, a real TDX Module CVE, which *does*
have an advisory: INTEL-SA-01397. **Intel TDX Base Architecture Specification
(348549-008) §17.3**; skill: `13-tdx.md` §13.21.2.

### trap-vtd-current-revision — 3/3

Cite **Rev 5.20, April 2026, order number D51397-019**. The landing page is stale;
*the current VT-d specification is Rev 4.1* has not been true since April 2026 —
the intel.com page metadata shows 2023-03-22 and its content endpoint was still
serving Rev 4.1 when checked on **2026-09-20**. **Always take the revision from the
PDF cover page, not from the intel.com page metadata.** One knock-on: Rev 5.20
renames first-level / second-level translation to **first-stage / second-stage**,
so use the Rev 5.20 spelling in anything you write. **Intel VT-d Architecture
Specification Rev 5.20 Ch.1**; skill: `10-vtd-dma-remapping.md` (Maps-to line),
`00-quickref.md` §0.1, `errata.md` E21.
