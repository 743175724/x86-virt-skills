## Failures

### 17 · dmar-register-offsets
**Asked:** "What are the register offsets in a VT-d remapping unit for the capability registers,
the global command and status registers, the root-table address and the interrupt-remap table
address?"
**Answered (verbatim, relevant clause):** "Offsets are relative to the unit's register base;
IOTLB registers and fault recording registers float and must be located from ECAP_REG.IRO and
CAP_REG.FRO."
**Missing:** `"the IOTLB registers and the fault recording registers are not at fixed offsets -
they come from ECAP_REG.IRO and CAP_REG.FRO, each scaled by 16"` — I named both capability
fields but dropped the `× 16` scaling, which is the load-bearing half of the item.
**Trap hit:** none
**Diagnosis:** *fact present but not surfaced.* The `X + (16 * Y)` rule is stated twice in the
chapter (§10.5.1 for FRO, §10.5.2 for IRO) but not in §10.5, where the offset table lives; the
table's preamble only says the offsets "must be read out of capability registers". A reader
answering an offsets question reads the table and stops.

### 23 · tdx-leaf-numbers
**Asked:** "What are the leaf numbers for entering a TD, for the host adding a private page
dynamically, and for the guest accepting one?"
**Answered (verbatim):** "Entering a TD = `SEAMCALL[TDH.VP.ENTER]`, leaf 0. Host adding a
private page dynamically = `SEAMCALL[TDH.MEM.PAGE.AUG]`, leaf 6 — adds a 4KB or 2MB private
page to an already-initialized TD, leaves the Secure-EPT entry PENDING and is *not* measured
(`TDH.MEM.PAGE.ADD`, leaf 2, is the build-time measured variant that contributes to MRTD).
Guest accepting one = `TDCALL[TDG.MEM.PAGE.ACCEPT]`, leaf 6, which zeroes the page content as
part of the operation. Citation: Intel TDX Module ABI Specification §5.4.81, §5.4.24 and
§5.5.3; Intel TDX Module Base Architecture Specification §9.10."
**Missing:** `"the leaf number is in RAX bits 15:0 for both SEAMCALL and TDCALL, with the
interface-function version in bits 23:16"`
**Trap hit:** none
**Diagnosis:** *fact present but not found — my method, not the chapter's fault.* The claim is
at 13-tdx.md §13.5 ("For a SEAMCALL to the TDX Module, RAX bits 15:0 select the leaf number,
bits 23:16 select the interface-function version number, and bit 63 must be 0") and again in
§13.6 for TDCALL. I located the leaf numbers by grepping for the leaf *names* and never read
the section preamble that defines the calling convention. A reader who opens §13.5 and reads
top-down gets this.

**Citation note for Q23.** `required_citation` is `TDX-ABI §5.4.1`; I cited `TDX-ABI §5.4.81`,

## Findings for the maintainer

### 1. Structure — the VT-d fault-reason range boundaries are in the wrong section (caused failure Q21)

The fact that fault-reason namespaces do not overlap (legacy 1h–Eh, interrupt-remapping
20h–2Bh, root-table-address programming 30h–34h, scalable-mode 38h–A5h) lives in
`12-vtd-faults-bios-siov.md` §12.9 "Pitfalls", item 2 — roughly 300 lines after §12.3.1, where
the legacy fault-reason table is. Any question of the form "my fault recording register shows
reason N" routes to §12.3, finds the answer, and stops; the stop rule the skill explicitly
teaches ("Stop. One chapter plus errata.md answers almost everything") actively encourages
stopping before §12.9.

The range boundaries are not a pitfall — they are the *first* thing a decoder needs, because
they decide which of the four tables to read. **Suggested fix:** move the four ranges into the
§12.3 preamble, immediately above "### 12.3.1 Legacy-mode fault reasons", as a claim line. The
existing preamble already describes the `L*` / `S*` / `RTA` / `HPT` condition-code prefixes but
gives no numeric ranges, which is exactly the half a reader cannot infer.

### 2. Structure — the `× 16` scaling for FRO and IRO is detached from the offset table (caused failure Q17)

`10-vtd-dma-remapping.md` §10.5 opens the register-offset table with "Two register groups — the
IOTLB registers and the fault recording registers — float, and their offsets must be read out
of capability registers", and the table's last two rows read `(from ECAP.IRO)` and
`(from CAP.FRO)`. Neither says the value is scaled: the actual rule, `X + (16 * Y)`, appears
only inside §10.5.1 (for FRO) and §10.5.2 (for IRO), which are capability-register-decode
sections a reader answering an offsets question has no reason to open.

**Suggested fix:** change the two table rows to `base + 16 × ECAP.IRO` and
`base + 16 × CAP.FRO`, or add the scaling to the §10.5 preamble sentence. One-line change; it
is the only numerically incomplete entry in an otherwise exemplary table.

### 3. Routing — 0 misses, but two rows overlap in a way that could bite a less careful reader

No routing miss occurred (24/24 first try), so there is no routing-table wording that *would
have* prevented a failure. Two near-misses are worth recording anyway, because in both cases
two rows matched and I had to pick:

- **Q2** ("tertiary controls … which MSR says which bits I may set") matched both
  `execution/exit/entry controls → 02-vmcs.md` and `capability MSRs → 08-vmx-instructions.md
  §8.4`. I chose 02 and it was right — but only because 02 §2.8.4 restates the MSR address,
  which is a controlled exception to the "cross-chapter restatement is prohibited" rule. An
  agent that took the prohibition literally would have routed to 08.
- **Q12 / Q13** ("which VMCS encodings for APICv / for the PID-pointer table") matched both
  `VMCS layout, field encodings → 02-vmcs.md §2.5` and `APICv … IPIv → 07-apic-virtualization.md`.
  07 was right for both; 07 §7.4 restates the encodings deliberately, saying so.

**Suggested wording**, added under the routing table: *"When a question asks for the encodings
or capability MSR of one named feature, read that feature's chapter — it restates what it
needs. `02` and `08` are the complete tables, for when you need the whole group."* This
converts two judgement calls into a rule.

### 4. Adjudication needed — Q23's `required_citation` does not match the anchors the chapter attaches to the asked-for facts

`tdx-leaf-numbers` asks only for three leaf numbers. In `13-tdx.md` those three claims carry
`[TDX-ABI §5.4.81]`, `[TDX-ABI §5.4.24]` and `[TDX-ABI §5.5.3]` respectively. The eval's
`required_citation` is `TDX-ABI §5.4.1`, which is the anchor on a *different* claim — the RAX
calling-convention claim that appears as the fourth `must_include` item.

**I think the eval is wrong here, not the chapter.** An answer that correctly answers the
question as asked, and correctly reproduces the anchors the chapter gives for exactly those
facts, fails a strict citation check. Two clean options:

- (a) accept `§5.4.81 / §5.4.24 / §5.5.3` as satisfying `required_citation` (list alternatives);
  or
- (b) reword the question stem so the calling convention is actually asked for — e.g. "…and how
  is the leaf number passed?" — which makes both the fourth `must_include` item and the
  `§5.4.1` anchor fair.

Option (b) is better: the RAX encoding is genuinely worth testing, it is just not something the
current stem asks about. As written, the item silently tests whether the answerer read the
section preamble rather than whether they can find a leaf number, and the citation requirement
then punishes the correct-but-narrow answer twice.

### 5. Minor — Q4's consolidated answer lives in a chapter the routing table does not point at

`exit-reasons-ept-family` is tagged `chapter: 05-vm-exit.md`, and the routing table sends
"exit reasons" to 05. In 05 the four numbers (48, 49, 62, 66) are scattered across a flat

genuinely good navigation aid that nothing points at. Consider referencing it from 05 §5.3, or
promoting the four-reason claim into `00-quickref.md`.
