## 11.1 What is encrypted, and by whom

AMD ships three distinct memory-encryption mechanisms that are frequently confused because they
share one hardware block — an AES engine in each on-die memory controller — and one page-table
attribute, the C-bit. They differ in *who decides which pages are encrypted* and *how many keys exist*:

| Mechanism | Who selects encrypted pages | Keys | Where documented |
|---|---|---|---|
| **SME** | the OS or hypervisor, per page, via the C-bit | one host key | APM2 §7.10 |
| **TSME** | nobody — firmware encrypts all DRAM unconditionally | one host key | AMD white paper (not the APM) |
| **SME-MK** | the OS or hypervisor, per page, via an EncrKeyID field | many host keys | APM2 §7.10.9 |
| **SEV / SEV-ES / SEV-SNP** | the guest, per page, via the C-bit | one key per ASID | APM2 §15.34–§15.36 → `12-sev.md` |

Everything in this chapter except the last row applies to a consumer part.

> **Sourcing note for `[MEM-WP 70363 p.<n>]`.** TSME, the cipher parameters and the AMD-SP's
> construction are documented only in AMD's *AMD Memory Encryption* white paper (pub. 70363,
> Kaplan / Powell / Woller, 2021-10-18), which is **non-normative**. It is cited here because it is a
> first-party AMD document and the alternative would be to leave real facts unsourced — but **where the
> white paper and the APM touch the same fact, the APM wins**, and every bit number, offset and CPUID
> field in this chapter is anchored to the APM or to a specification instead. The paper carries no
> printed folio, so `p.<n>` is the PDF page number.

- **Claim.** SME lets software running in non-virtualized (native) mode mark individual pages of memory as encrypted through the page tables; a page marked encrypted is automatically decrypted when read by software and automatically encrypted when written to DRAM.  `[APM2 §7.10]` `[1]` `C:high` `V:durable`
- **Claim.** All memory encrypted using SME is encrypted with the **same AES key, created randomly each time the system is booted**, and that key can neither be read nor modified by software.  `[APM2 §7.10]` `[1]` `C:high` `V:durable`
- **Claim.** The encryption is performed by a dedicated AES engine inside each on-die memory controller, using a **128-bit key** in a mode that adds a **physical-address-based tweak** so that moving a ciphertext block to a different address does not decrypt to the same plaintext. The APM states neither the key size nor the mode.  `[MEM-WP 70363 p.4]` `[16]` `C:medium` `V:durable`
- **Claim.** The key is generated by the AMD Secure Processor (AMD-SP) from an on-board NIST SP 800-90-compliant hardware random number generator and is held in dedicated hardware registers that never expose it outside the SOC in the clear; unlike SEV, **SME does not require software on the CPU cores to participate in key management**. The APM names the AMD-SP as the key manager for SEV but says nothing about the entropy source.  `[MEM-WP 70363 p.4]` `[16]` `C:medium` `V:durable`
- **Claim.** SME is supported in all CPU modes in which **CR4.PAE=1 and paging is enabled** — long mode and legacy PAE-enabled protected mode.  `[APM2 §7.10.3]` `[1]` `C:high` `V:durable`
- **Claim.** SME remains available while the processor executes in SMM once SMM has enabled paging, and any physical-address restriction imposed by memory encryption stays in force in SMM.  `[APM2 §7.10.7]` `[1]` `C:high` `V:durable`

The threat SME addresses is physical: cold-boot readout, DRAM interface snooping, and removal of an
NVDIMM with the data intact. It does **not** isolate software from software on the same host — a
kernel-mode attacker holding the page tables can simply read the plaintext through them. Software
isolation is what SEV adds, and that is `12-sev.md`.

- **Claim.** SME protects the contents of DRAM against physical attacks on the system; it is not a mechanism for isolating one piece of host software from another.  `[APM2 §7.10]` `[1]` `C:high` `V:durable`

## 11.2 Enumerating memory encryption: `Fn8000_001F`

`Fn8000_001F` is the single leaf that answers "what memory encryption does this part have, and how do I
use it". Its four registers carry, respectively, a feature bitmap, the geometry of the C-bit, the ASID
ceiling and the ASID floor. **Read it before touching anything in this chapter**; every value below is
implementation-specific and none of it may be hardcoded.

The full EAX bitmap, verbatim from AMD's field table:

| 29 | `NestedVirtSnpMsr` | `VIRT_RMPUPDATE` (C001_F001h) and `VIRT_PSMASH` (C001_F002h) supported |

- **Claim.** `Fn8000_001F_EAX` is AMD's memory-encryption feature bitmap and defines every bit listed above, from `SME` at bit 0 through `IbpbOnEntry` at bit 31; bit 4 is `SEV-SNP` and bit 5 is `VMPL`, whose semantics are `14-sev-snp.md`.  `[APM3 App.E]` `[2]` `C:high` `V:durable`
- **Claim.** `Fn8000_001F_EBX` carries three packed fields: **`CbitPosition` in bits 5:0** (the C-bit's location in a page-table entry), **`PhysAddrReduction` in bits 11:6** (the physical-address bit reduction), and **`NumVMPL` in bits 15:12** (the number of VM permission levels); bits 30:16 are reserved and bit 31 is `COHERENCY_SFW_NO`, which indicates that the software workaround for the SEV-SNP cache-coherency issue of AMD-SB-3017 is not needed.  `[APM3 App.E]` `[2]` `C:high` `V:durable`
- **Claim.** `Fn8000_001F_ECX[31:0]` is `NumEncryptedGuests`, the number of encrypted guests supported simultaneously, and `Fn8000_001F_EDX[31:0]` is `MinSevNoEsAsid`, the minimum ASID value usable by a guest that enables SEV with SEV-ES disabled.  `[APM3 App.E]` `[2]` `C:high` `V:durable`
- **Claim.** Support for the memory-encryption features is reported in `Fn8000_001F[EAX]`; when the feature is present, `Fn8000_001F[EBX]` supplies the additional information needed to use it, including which page-table bit marks a page encrypted.  `[APM2 §7.10.1]` `[1]` `C:high` `V:durable`
- **Claim.** The APM directs readers to **Volume 3 section E.4.17** for the complete CPUID detail of the encrypted-memory features, which is the leaf's normative field table.  `[APM2 §7.10.1]` `[1][2]` `C:high` `V:durable`

Three fields in the table above belong to other chapters' subjects even though this chapter owns the
table: `ECX`/`EDX` drive the ASID partition in `12-sev.md`, `EBX[15:12]` drives the level count in
`14-sev-snp.md`, and `EAX[16]` (`VTE`) is a VMCB control described in `12-sev.md`.

### 11.2.1 Probing discipline

`Fn8000_001F` is a plain leaf with no subfunction, so probing it is cheap and there is no excuse for
hardcoding. Two habits matter:

- Test the *feature* bit before reading any dependent field. `CbitPosition` is only meaningful when
  `EAX[0]` is set; `NumVMPL` only when `EAX[5]` is set.
- Read back rather than assume. A part can report `SME` without reporting `SEV`, and reports
  `SEV-SNP = 0` while still reporting `SEV = 1` — see §11.8.

- **Claim.** A hypervisor that enables SEV must check the guest's ASID against `Fn8000_001F_ECX[NumEncryptedGuests]`, because VMRUN terminates with `VMEXIT_INVALID` if the ASID exceeds that maximum — one of three SEV consistency checks, the others being that nested paging is enabled and that `HWCR[SmmLock]` is set (`12-sev.md`).  `[APM2 §15.34.3]` `[1]` `C:high` `V:durable`

### 11.2.2 A worked decode

`EBX` is the register people get wrong, because three fields are packed into its low 16 bits and the
temptation is to use the whole register as a position. Decoding a real value takes three masks:

```
EBX = 0000_0173h
  CbitPosition      = EBX        & 0x3F  = 0x33 = 51
  PhysAddrReduction = (EBX >> 6) & 0x3F  = 0x05 = 5
  NumVMPL           = (EBX >> 12) & 0xF  = 0x0  = 0   (no VMPL support on this part)
```

Two working rules follow. First, the C-bit position and the physical-address reduction are
**independent fields**: the manual defines each separately and never states an arithmetic relationship
between them, so deriving one from the other is a guess. Second, `CbitPosition` can name a bit above the
part's reported physical-address width — `Fn8000_0008_EAX[7:0]` — in which case the C-bit is a
page-table attribute bit rather than an address bit and no address space is lost to it directly.

- **Claim.** The physical-address width the processor implements is reported separately, in `Fn8000_0008_EAX[7:0]` (`PhysAddrSize`), and `Fn8000_001F_EBX` neither contains it nor is derivable from it.  `[APM3 App.E]` `[2]` `C:high` `V:durable`
- **Claim.** All three `Fn8000_001F_EBX` fields are read with independent masks — `EBX & 3Fh`, `(EBX >> 6) & 3Fh` and `(EBX >> 12) & Fh` — and a decode that treats the low byte as a position is wrong whenever `PhysAddrReduction` is non-zero.  `[APM3 App.E]` `[2]` `C:high` `V:durable`

## 11.3 The C-bit

The C-bit ("enCrypted bit") is the page-table attribute that selects encryption for a page. Its
position is **implementation-specific** and must be read from `Fn8000_001F_EBX[5:0]`.

- **Claim.** Software selects encryption per page through the page tables; the location of the C-bit is implementation-specific and is determined by reading `Fn8000_001F[EBX]`, and in some implementations the bit used is a physical address bit — the APM's own example is address bit 47.  `[APM2 §7.10.4]` `[1]` `C:high` `V:durable`
- **Claim.** Setting the C-bit to 1 marks the page encrypted in DRAM and clearing it to 0 leaves the page unencrypted; the C-bit may be applied to translation-table entries for **any page size — 4 KB, 2 MB or 1 GB**.  `[APM2 §7.10.4]` `[1]` `C:high` `V:durable`
- **Claim.** The page tables themselves may live in encrypted memory: if the C-bit is set in a PML4 entry, the PDP table it points to — and therefore every PDPE in that table — is loaded from encrypted memory.  `[APM2 §7.10.4]` `[1]` `C:high` `V:durable`
- **Claim.** In legacy PAE mode, if the C-bit location falls in the upper 32 bits of a page-table entry, the first-level (PDP) table **cannot** be located in encrypted memory, because CR3 is only 32 bits wide in 32-bit PAE mode.  `[APM2 §7.10.6]` `[1]` `C:high` `V:durable`

### 11.3.1 Physical-address bit reduction

- **Claim.** On some implementations the processor's physical-address size is **reduced when memory encryption features are enabled** — the APM's worked example is a reduction from 48 to 43 bits — and the upper physical-address bits then become reserved except where otherwise indicated; the reduction present is reported in `Fn8000_001F[EBX]`.  `[APM2 §7.10.1]` `[1]` `C:high` `V:durable`
- **Claim.** Bits that become reserved in this mode are treated exactly like any other reserved page-table bit: a non-zero value in one of them during address translation generates a **page fault**.  `[APM2 §7.10.1]` `[1]` `C:high` `V:durable`
- **Claim.** Before setting `SYSCFG[MemEncryptionModEn]`, software on an implementation that reduces the physical-address size **must already be executing from addresses whose upper physical-address bits are 0**, or it will fault itself out of existence at the moment encryption is enabled.  `[APM2 §7.10.2]` `[1]` `C:high` `V:durable`

The per-generation values of `CbitPosition` and `PhysAddrReduction` are version-bearing and belong to
`90-dated-landscape.md`. What is durable is that they differ between parts and must be read at runtime.

### 11.3.2 The C-bit is not an address bit for range checks, and MMIO must be clear

This is the rule device drivers trip over.

- **Claim.** On implementations that reduce the physical-address size, memory range checks that decide memory type or DRAM-versus-MMIO — MTRR, TOM, IORR and so on — are performed using the **reduced** physical address size, and the C-bit is **not** considered a physical address bit and is masked by hardware for the purpose of those checks.  `[APM2 §7.10.5]` `[1]` `C:high` `V:durable`
- **Claim.** Any page corresponding to an MMIO address **must** be configured with the C-bit clear; encrypted I/O pages are not allowed and an access with the C-bit set is **ignored**.  `[APM2 §7.10.5]` `[1]` `C:high` `V:durable`
- **Claim.** DMA to SME-encrypted memory is supported and from a device's standpoint is an ordinary memory access with the C-bit set; devices that cannot generate that address bit — legacy 32-bit devices, in AMD's example — are accommodated by using the IOMMU to remap device request addresses to addresses with the C-bit set (`09-iommu-page-tables.md`). The APM's §7.10.5 covers MMIO and range checks but not DMA to encrypted DRAM.  `[MEM-WP 70363 p.5]` `[MEM-WP 70363 p.6]` `[16]` `C:medium` `V:durable`

Under SEV the guest's C-bit is masked out of the guest physical address before the nested-page-table
walk and reapplied to the resulting system physical address (sPA); see `06-nested-paging.md` for where
the bit sits in a nested entry and `12-sev.md` for the guest/host precedence rule.

## 11.4 Cache coherence when the C-bit changes

Get this wrong and the failure is silent data corruption, not a fault.

- **Claim.** In some hardware implementations coherency between the encrypted and unencrypted mappings of the same physical page is **not enforced**; on such a system software must flush the page from **all** CPU caches in the system before changing the value of the C-bit for that page.  `[APM2 §7.10.6]` `[1]` `C:high` `V:durable`
- **Claim.** The flush is **not** required when the implementation supports coherency across encryption domains, which is reported by **`Fn8000_001F_EAX[10]`** (`HwEnfCacheCoh`).  `[APM2 §7.10.6]` `[1]` `C:high` `V:durable`
- **Claim.** Changing the value of a C-bit on a page does **not** re-encrypt the page's existing contents; any data present before the modification becomes unintelligible afterwards.  `[APM2 §7.10.6]` `[1]` `C:high` `V:durable`

### 11.4.1 Encrypt-in-place

To turn encryption on for a page while keeping the data, AMD specifies an exact algorithm. It exists
because a line cannot be copied in place: the refill that precedes the write would decrypt garbage, and
an eviction between the two halves of a naive copy corrupts the unwritten part.

- **Claim.** AMD's in-place encryption algorithm is: (1) create two linear mappings X and Y of the same physical page, X with C-bit 0 and the **WP** memory type and Y with C-bit 1 and the **WB** memory type; (2) execute `WBINVD` on all cores in the system; (3) copy N bytes from X to a temporary buffer in conventionally-mapped memory, where **N equals the L1 cache line size reported by `Fn8000_0005[ECX]`**; (4) write those N bytes from the temporary buffer to Y; (5) repeat steps 3–4 until the whole page has been copied.  `[APM2 §7.10.8]` `[1]` `C:high` `V:durable`
- **Claim.** The copy must go through a temporary buffer rather than in place because the initial cache refill of the line in step 4 decrypts it — corrupting it, since it is not yet encrypted — and step 4 is what restores the original contents.  `[APM2 §7.10.8]` `[1]` `C:high` `V:durable`

Under SEV the same problem recurs with a guest key involved, and `WBINVD` on every core the guest ran on
is expensive; AMD therefore adds the `VMPAGE_FLUSH` MSR. That MSR belongs to `12-sev.md`.

## 11.5 SME versus TSME

SME's flexibility is also its cost: it needs the OS or hypervisor to manage the C-bit in every page
table, including the tables themselves. TSME removes that requirement by removing the choice.

- **Claim.** SME requires support in the OS or hypervisor; **Transparent SME (TSME)** is the option for systems that want the physical protection of SME decoupled from the OS/HV, and under TSME **all memory is encrypted regardless of the value of the C-bit on any particular page**. **The APM does not contain the term TSME at all**; the only description AMD publishes is this white paper, which is non-normative.  `[MEM-WP 70363 p.6]` `[16]` `C:medium` `V:durable`
- **Claim.** TSME is enabled by a **BIOS setting** on supported platforms and requires no software modification; AMD markets it as AMD Memory Guard. Again, the APM does not describe this; the source is non-normative.  `[MEM-WP 70363 p.6]` `[16]` `C:medium` `V:durable`
- **Claim.** TSME is visible to AMD firmware as a platform property rather than a CPU feature bit: the SEV-SNP firmware ABI reports it as **`TSME_EN`, bit 1 of the `PLATFORM_INFO` field**, described as "indicates that TSME is enabled in the system" (the surrounding structure is owned by `14-sev-snp.md`).  `[SNP-ABI 1.59 Table 28]` `[10]` `C:high` `V:durable`
- **Claim.** Full memory encryption under plain SME is achieved by the OS or hypervisor setting the C-bit in **all** DRAM physical addresses in **all** page tables — instruction pages, data pages, and the pages holding the page tables — which is exactly the work TSME removes. The APM describes the C-bit mechanism but not this usage model.  `[MEM-WP 70363 p.5]` `[16]` `C:medium` `V:durable`
- **Claim.** A hypervisor can use SME for partial encryption instead, setting the C-bit only in the nested page-table entries that back guest VMs, which encrypts VM memory without any modification to the guests — but with the **host** key, so it protects against a physical attacker and not against the hypervisor. Usage model; the APM does not describe it.  `[MEM-WP 70363 p.5]` `[16]` `C:medium` `V:durable`

**Which one is running on a given PC** is a firmware decision, not an OS decision, and TSME is the form
that applies with no operating-system participation at all. What a particular operating system does
with SME — including whether it manages the C-bit per page — is out of scope here; for Windows see
`16-windows-platform.md`.

> **Linux-only footnote.** The Linux kernel exposes a three-state view of SME — *Supported* (the CPU
> reports it via CPUID), *Enabled* (supported **and** bit 23 of `MSR_AMD64_SYSCFG` is set), and *Active*
> (supported, enabled, and the kernel is actively applying the encryption bit to page-table entries) —
> and takes `mem_encrypt=on` on the kernel command line. If the BIOS does not enable SME, Linux cannot
> activate it whatever the command line says. There is no equivalent switch on Windows; this paragraph
> is here so that a reader arriving from Linux documentation knows it does not transfer.

- **Claim.** **Linux-only.** Linux defines SME as *Supported* / *Enabled* / *Active*, where *Enabled* additionally requires bit 23 of `MSR_AMD64_SYSCFG` to be set and *Active* additionally requires the kernel to be applying the encryption bit to page-table entries; if the BIOS has not enabled SME the kernel cannot activate it even with `mem_encrypt=on`. No AMD specification defines these states — they are a kernel construct.  `[no-spec]` `[331]` `C:high` `V:durable`

### 11.5.1 Multi-key SME (SME-MK)

SME-MK is the third form, and the one nobody can find documentation for because it lives in a single
subsection at the end of the memory chapter rather than anywhere near SEV.

- **Claim.** Multi-Key Secure Memory Encryption (SME-MK) extends SME by letting the OS or hypervisor load encryption keys into the hardware memory controllers and select which key encrypts each page; loading the keys requires the AMD Secure Processor.  `[APM2 §7.10.9]` `[1]` `C:high` `V:durable`
- **Claim.** SME-MK support is reported by **`Fn8000_0023_EAX[MemHmk]` (bit 0)**, and the number of simultaneously available host encryption key IDs by **`Fn8000_0023_EBX[MaxMemHmkEncrKeyID]` (bits 15:0)**; `Fn8000_0023_ECX` and `EDX` are reserved.  `[APM3 App.E]` `[2]` `C:high` `V:durable`
- **Claim.** SME-MK is enabled by setting **SYSCFG bit 26 (`HostMultiKeyMemEncrModeEn`) to 1 and bit 23 (`MemEncryptionModEn`) to 0** — the two modes are mutually exclusive, not cumulative.  `[APM2 §7.10.9]` `[1]` `C:high` `V:durable`
- **Claim.** When SME-MK is enabled every system physical address carries an `EncrKeyID` field — including CR3, the nested page-table base and VMCB addresses — an `EncrKeyID` of zero means the access is not encrypted, `EncrKeyIdWidth` equals `log2(Fn8000_0023_EBX[MaxMemHmkEncrKeyID] + 1)`, and the field occupies system physical address bits **`[CBitP : CBitP − EncrKeyIdWidth + 1]`** where `CBitP` is `Fn8000_001F_EBX[CbitPosition]`.  `[APM2 §7.10.9]` `[1]` `C:high` `V:durable`

Note the consequence of that last claim: SME-MK consumes the C-bit position and the bits below it, so
the physical-address reduction reported in `Fn8000_001F_EBX[PhysAddrReduction]` is what pays for the
key-ID field.

## 11.6 SYSCFG and firmware enablement

Every memory-encryption mode on an AMD part is gated by one MSR.

- **Claim.** The system-configuration register SYSCFG is an MSR at address **`C001_0010h`**.  `[APM2 §3.2.1]` `[1]` `C:high` `V:durable`

| Bit | Name | Effect |
|---|---|---|
| 22 | `Tom2ForceMemTypeWB` | forces WB between 4 GB and `TOP_MEM2` |
| 23 | `MemEncryptionModeEn` | enables SME and SEV |
| 24 | `SecureNestedPagingEn` | enables SEV-SNP |
| 25 | `VMPLEn` | enables the VMPL feature |
| 26 | `HostMultiKeyMemEncrModeEn` | enables SME-MK |

- **Claim.** SYSCFG **bit 23 `MemEncryptionModeEn`** enables the SME and SEV memory-encryption features and, once either it or `HostMultiKeyMemEncrModeEn` has been set to 1, **it cannot be changed**.  `[APM2 §3.2.1]` `[1]` `C:high` `V:durable`
- **Claim.** SYSCFG **bit 24 `SecureNestedPagingEn`** enables SEV-SNP, cannot be changed once set, and can only be set if `MemEncryptionModeEn` is already set or is being set simultaneously; SYSCFG **bit 25 `VMPLEn`** enables the VMPL feature and should be set to 1 when `SecureNestedPagingEn` is being set, after which it can no longer be changed (the SNP side of this is `14-sev-snp.md`).  `[APM2 §3.2.1]` `[1]` `C:high` `V:durable`
- **Claim.** SYSCFG **bit 26 `HostMultiKeyMemEncrModeEn`** enables SME-MK and, like bit 23, is write-once.  `[APM2 §3.2.1]` `[1]` `C:high` `V:durable`
- **Claim.** Prior to using SME, software must set SYSCFG bit 23 to 1; encryption is then controlled further through the page tables.  `[APM2 §7.10.2]` `[1]` `C:high` `V:durable`
- **Claim.** Software should keep `SYSCFG[MemEncryptionModEn]` **consistent across all CPU cores in the system**; failing to do so "may lead to unexpected results", and the same consistency requirement applies to `HostMultiKeyMemEncrModeEn`.  `[APM2 §7.10.2]` `[1]` `C:high` `V:durable`

> **Spelling.** AMD writes the bit-23 field name **`MemEncryptionModeEn`** in the SYSCFG register
> description (§3.2.1) and **`MemEncryptionModEn`** — without the second `e` — throughout §7.10. Both
> spellings are AMD's own and refer to the same bit. Linux uses `MSR_AMD64_SYSCFG` bit 23.

- **Claim.** After `SecureNestedPagingEn` is set to 1, writes to the SYSCFG MSR itself are **ignored**, while writes to the fixed-range MTRRs, the IORRs, `TOP_MEM`, `TOP_MEM2` and `SMM_KEY` produce `#GP(0)`; the memory map is frozen for the life of the boot.  `[APM2 §15.36.2]` `[1]` `C:high` `V:durable`

That last claim is the reason firmware, not the OS, owns this register: by the time an OS runs, the
window in which these bits can be set has usually closed.

## 11.7 AMD-SP on a client part

The AMD Secure Processor is the second processor on the die, and it holds every memory-encryption key
in the system. It is named in the APM but not specified there.

- **Claim.** Key management for the memory-encryption features is not handled by the x86 cores but by a separate processor, the **AMD Secure Processor (AMD-SP)**, present on AMD SOCs; the APM states explicitly that a detailed discussion of AMD-SP operation is beyond its scope.  `[APM2 §15.34.2]` `[1]` `C:high` `V:durable`
- **Claim.** The AMD-SP is a **32-bit ARM Cortex-A5 microcontroller** functioning as a dedicated security subsystem integrated within the AMD SOC. The APM names the AMD-SP and then states that its operation is beyond the manual's scope.  `[MEM-WP 70363 p.4]` `[16]` `C:medium` `V:durable`
- **Claim.** Loading encryption keys for SME-MK requires the AMD-SP.  `[APM2 §7.10.9]` `[1]` `C:high` `V:durable`
- **Claim.** On an SNP-enabled system the hypervisor asks the AMD-SP to finalize initialization of the Reverse Map Table, after which the AMD-SP prevents all software from writing that memory directly (`14-sev-snp.md`).  `[APM2 §15.36.4]` `[1]` `C:high` `V:durable`

The AMD-SP is also where a client platform's firmware TPM runs, which is why it appears in conversations
about Windows 11's TPM requirement. That part is undocumented in the specification corpus:

- **Claim.** Neither the AMD64 Programmer's Manual nor AMD's memory-encryption white paper describes the firmware TPM (fTPM) implementation hosted on the AMD-SP; the APM's only TPM content is the **discrete** LPC-attached TPM used by `SKINIT` (`17-security.md`), and the platform TPM requirement itself is a Windows fact belonging to `16-windows-platform.md`.  `[no-spec]` `[1][16]` `C:high` `V:durable`

## 11.8 What a client part does not have

This section exists because the sentence people reach for — "SEV does not exist on client parts" — is
false, and a Zen 2 or Zen 3 desktop disproves it in one `cpuid` invocation. The defensible statements
are narrower and they are the ones this skill uses.

Measured `Fn8000_001F` words from published CPUID dumps of shipping client parts:

| Part (client, non-PRO unless noted) | EAX | EBX | ECX | EDX |
|---|---|---|---|---|
| Ryzen 5 3600X (Matisse, Zen 2) | `0001000F` | `0000016F` | `000001FD` | `00000001` |
| Ryzen 7 5800X (Vermeer, Zen 3) | `0001780F` | `00000173` | `000001FD` | `00000001` |
| Ryzen 7000 desktop (Raphael, Zen 4) | `00000001` | `000000B3` | `00000000` | `00000000` |
| Ryzen 9 9950X (Granite Ridge, Zen 5) | `00000001` | `000000B3` | `00000000` | `00000000` |

- **Claim.** Client Zen 2 and Zen 3 desktop parts report `Fn8000_001F_EAX` with bits 0–3 set — `SME`, `SEV`, `PageFlushMsr` and `SEV-ES` — and `ECX = 1FDh`, i.e. **509** simultaneously encryptable guests; on Zen 4 and Zen 5 client parts the same register reads `00000001`, i.e. **`SME` only**, with `ECX` and `EDX` zero.  `[no-spec]` `[330]` `C:medium` `V:durable`
- **Claim.** **`Fn8000_001F_EAX[4]` (`SEV-SNP`) is clear on every client part in that measurement set**, including the Zen 2 and Zen 3 parts that do report `SEV`; SEV-SNP has never been set on a client part.  `[no-spec]` `[330][35]` `C:medium` `V:durable`
- **Claim.** Writing "`Fn8000_001F EAX[1]` reads 0 on Ryzen" is therefore **wrong** rather than merely imprecise; the correct client statement is about TSME, and the correct SEV statement is that SEV is *productised* on EPYC (`errata.md` E12, `12-sev.md`).  `[no-spec]` `[330]` `C:medium` `V:durable`

The per-generation mapping of key-slot counts to EPYC generations is an **open conflict** and is not
settled here — see `errata.md` O1. The 509 above is a measured client value, not a claim about any EPYC
generation.

What a client PC genuinely does not get:

- **Claim.** A guest on a client part cannot be memory-encrypted with a per-VM key on Zen 4 or later client silicon, because `Fn8000_001F_EAX[1]` is clear there and SEV cannot be enabled when it is: if `MemEncryptionModEn` is 0 the VMCB control bit for SEV is ignored outright, and the feature bit gates everything above it (`02-vmcb.md`, `12-sev.md`).  `[APM2 §15.34.3]` `[1][330]` `C:medium` `V:durable`
- **Claim.** Windows' VBS, HVCI and Credential Guard are built on SLAT (nested paging) and the IOMMU, not on SEV; Microsoft's hardware requirements for virtualization-based security name virtualization extensions and an IOMMU, and no SEV-family feature appears among them.  `[42]` `C:medium` `V:durable`

### 11.8.1 Answering the client question

"Can my Ryzen laptop use AMD memory encryption?" The answer is **yes, via TSME**, and it is worth
separating the three things a reader might be asking:

| Question | Where the answer lives | How to get it |
|---|---|---|
| Can this CPU encrypt DRAM at all? | `Fn8000_001F_EAX[0]` (`SME`) | read CPUID |
| Is the whole of DRAM actually being encrypted? | firmware state | firmware setup: "TSME", "AMD Memory Guard", "Transparent SME" |
| Can this CPU run a confidential VM? | `Fn8000_001F_EAX[1]` / `EAX[4]` | read CPUID; on Zen 4+ client parts both are 0 |

The trap is conflating rows one and two. `EAX[0]` reporting `SME` says the *CPU* can do it; whether
TSME is switched on is a firmware state and is **not** reflected in any CPUID bit or in SYSCFG bit 23,
which gates OS-driven SME rather than firmware-driven TSME.

- **Claim.** CPUID reports memory-encryption **capability**, not whether encryption is currently in effect: the APM's discovery text for SME is a support statement, and the enable lives in SYSCFG and — for TSME — in firmware, so a part reporting `Fn8000_001F_EAX[0] = 1` says nothing about whether its DRAM is encrypted right now.  `[APM2 §7.10.1]` `[1]` `C:high` `V:durable`

## 11.9 Open items

- **The C-bit's relationship to the reported physical-address size is not obvious from the manual.**
  The measured Zen 3 and Zen 4 client parts report `CbitPosition = 51` while `Fn8000_0008_EAX[7:0]`
  reports a 48-bit physical address, so the C-bit is not an implemented address bit there, yet
  `PhysAddrReduction` is still non-zero (5 and 2 respectively). The APM describes the reduction and the
  C-bit position as separate fields and never states the relationship between them. Do not derive one
  from the other.
- **TSME has no normative specification.** Everything in §11.5 about TSME comes from AMD's
  memory-encryption white paper and one `PLATFORM_INFO` field in the SNP firmware ABI. The APM does not
  contain the string "TSME". If a normative description exists it is in a PPR, and **AMD publishes no
  PPR for client Ryzen**, so this gap is unlikely to close.
- **The fTPM is undocumented in this corpus** (see §11.7). The claim that it runs on the AMD-SP is
  widely repeated and nowhere specified in the documents this skill cites.
- **`COHERENCY_SFW_NO` (`EBX[31]`) points at AMD-SB-3017**, which is not in this skill's bibliography;
  the advisory itself belongs to `17-security.md` and has not been fetched.
- **Whether a given client platform's firmware exposes the TSME switch at all** is an OEM decision and
  is not discoverable from CPUID. This chapter cannot answer "is it on?" — only "can it be".
